
# Architectural Blueprint for a SAPT Workflow Automation System

## Introduction and Goals

Symmetry-Adapted Perturbation Theory (SAPT) calculations are computationally intensive and involve complex interactions between quantum chemistry codes and hardware resources. Automating SAPT computations requires a **robust, Python-based workflow system** that can scale from a local workstation to HPC clusters ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=This%20complexity%20increase%20is%20due,number%20of%20computations%20scale%20up)) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=managers%20differ%20depending%20on%20the,other%20management%20systems%20mentioned%20above)). The goal is to design a **modular** architecture that integrates with existing quantum chemistry tools (Psi4, CamCASP, SAPT2020) and supports both local parallelism and distributed execution. Key objectives include:

- **Seamless Integration with QC Backends:** Use Psi4 as the default engine (via its Python API) and provide optional plugins for CamCASP and SAPT2020. This allows leveraging each code’s capabilities without exposing backend-specific complexity to the user.
    
- **Local and Distributed Execution:** Enable efficient local runs using Python’s multiprocessing (up to 8 concurrent jobs) and scale out to clusters using Dask for distributed task execution. Integration with SLURM should allow submitting jobs to managed HPC resources when needed.
    
- **Modular API Design:** Achieve a clear separation of concerns – user-facing API/configuration, workflow orchestration logic, and backend-specific operations – to balance flexibility with ease of use. Users should be able to run common tasks with simple function calls, yet the system should be extensible for advanced customization.
    
- **Robust Error Handling:** Implement fault-tolerant patterns suitable for high-throughput quantum chemistry workflows ([Open Chemistry, JupyterLab , REST , and quantum chemistry (Journal Article) | NSF PAGES](https://par.nsf.gov/biblio/10453965-open-chemistry-jupyterlab-rest-quantum-chemistry#:~:text=property%20data%20while%20also%20enabling,Overall)). The system should detect and handle common calculation failures (convergence issues, resource exhaustion, etc.), perform retries or adjustments when possible, and log errors without crashing the entire workflow.
    
- **Reproducibility and State Management:** Provide mechanisms to record the inputs, outputs, and execution state of each calculation for provenance and reproducibility ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=in%20large%20amounts%20of%20interconnected,recursively%29%20their%20respective%20provenance)) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=match%20at%20L486%20the%20execution,in%20turn%20be%20used%20as)). This includes tracking configurations, software versions, and results so that runs can be audited or resumed if interrupted.
    

By surveying existing workflow frameworks (AiiDA, ASE, QCFractal/QCArchive) and adopting their best practices, this design will ensure a **scalable, maintainable, and user-friendly** solution for automating SAPT computations.

## System Architecture Overview

(image) _High-level architecture of the SAPT workflow system, highlighting modular components and execution on local or cluster resources._

At a high level, the system consists of a **Workflow Manager** (core Python application) that interfaces between the user and the quantum chemistry codes. The architecture (shown above) is designed in layers to separate functionality:

- **User Interface Layer:** Provides an API (and optionally CLI or notebook interface) through which users configure SAPT jobs and submit workflows. This could be a Python library interface (e.g. a `submit_sapt_calculation()` function or a `SAPTWorkflow` class) that accepts user input such as molecular data, desired SAPT level, and execution settings.
    
- **Workflow Orchestrator (Engine):** The orchestrator is the “brain” of the system. It reads user configurations, breaks down the requested work into discrete tasks (e.g. individual SAPT calculations), and schedules these tasks for execution. It manages the job queue and decides whether to execute tasks locally or send them to a distributed scheduler. This component is also responsible for collecting results and updating task states.
    
- **Backend Interface Layer:** A set of **backend modules or plugins** that know how to talk to specific quantum chemistry programs (Psi4, CamCASP, SAPT2020). Each backend module implements a common interface (e.g. a `SAPTBackend` abstract base class) with methods to **prepare inputs**, **invoke the computation**, and **parse outputs** for that software. The orchestrator delegates all code-specific logic to these backend classes. This mirrors the abstraction used in ASE’s “calculator” interface, which allows different computational engines to be plugged in under a common API ([ASE](https://rosengroup.slite.page/p/BGJeKFLJdSPpJK/ASE#:~:text=The%20%20Atomic%20Simulation%20Environment,throughput%20calculations)). For example, a `Psi4Backend` might call Psi4’s Python API directly, whereas a `CamCASPBackend` might write an input file and run an external CamCASP binary.
    
- **Execution Layer:** Handles actual execution of tasks on compute resources. The system supports two modes: **local parallelism** via a multiprocessing pool (e.g. up to 8 parallel processes on the local machine) and **distributed execution** via Dask. In local mode, the orchestrator spawns worker processes that run SAPT tasks concurrently (limited by CPU cores). In distributed mode, the orchestrator connects to a Dask scheduler which dispatches tasks to **Dask workers** (which may be on an HPC cluster). This design allows a single codebase to scale from a laptop to a multi-node cluster ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=QCArchive%20is%20a%20platform%20that,retrieval%20and%20analysis%2C%20or%20export)). The architecture optionally interfaces with **SLURM** for cluster job scheduling – either by using Dask’s job-queue integration to launch workers on the cluster or by direct submission of jobs through SLURM (for example, using Dask-Jobqueue’s `SLURMCluster` or generating `sbatch` scripts).
    
- **State Management & Logging:** Cross-cutting the above layers is a mechanism for tracking the state of each task (queued, running, finished, failed) and storing relevant data. This could be a lightweight database or file-based storage that the Workflow Manager uses to record what has been done and to enable **restarts without losing progress** ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=match%20at%20L422%20only%20when,the%20engine%20will%20keep%20waiting)). Also, a logging subsystem captures output and errors from each calculation for debugging and provenance.
    
- **Error Handling Component:** Another cross-cutting layer that intercepts errors at each stage (input generation, execution, output parsing). Rather than a single module, error handling is implemented via consistent patterns (try/except wrappers, validation checks, and error-recovery routines) throughout the orchestrator and backend implementations. This ensures that one failed task doesn’t crash the entire workflow and that common errors can be automatically addressed (described in detail in a later section).
    

Overall, the architecture is **modular and service-oriented** – each part (user API, orchestrator, backends, execution engine) has a clear role and interface. This separation makes the system easier to maintain and extend (e.g. adding a new backend or swapping the execution layer) without affecting other parts of the code.

## Component Design and Responsibilities

**1. User API and Configuration:** The user-facing API should be simple yet flexible. We design a high-level Python API where users can configure calculations either by passing Python objects or by using a configuration file (YAML/JSON) that the library can read. For example, a user might create a `SAPTJob` object with the two monomer geometries, basis set, and desired SAPT level, then add it to a `SAPTWorkflow` and run it. The API will provide sensible defaults (e.g. use Psi4 by default, use all available local cores unless specified, etc.) to make common cases easy. For advanced usage, users can override settings like which backend to use or specific Psi4 options. The API design mirrors AiiDA’s approach of providing a high-level workflow abstraction while still allowing low-level control when needed ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=run%20by%20the%20engine%2C%20is,output%2C%20given%20certain%20data%20as)) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=subprocesses%2C%20but%20this%20quickly%20becomes,job%20schedulers%2C%20and%20work%20chains)). Key design points for the API:

- **Simple Workflows:** e.g. `result = sapt.compute(molA, molB, method="SAPT0", backend="psi4")` would handle everything internally.
    
- **Batch Operations:** Allow specifying multiple calculations in one workflow (e.g. a list of molecule pairs) to exploit parallelism.
    
- **Configuration Object:** Use a Python dataclass or dictionary for configuration (with fields like `backend`, `basis_set`, `enable_bsse_correction`, `parallel_mode`, etc.), so it’s easy to extend with new options.
    
- **CLI/Notebook Integration:** Optionally provide a CLI command (for non-Python users) that reads input files and a config, or Jupyter notebook widgets for interactive use.
    

**2. Workflow Orchestrator / Scheduler:** The orchestrator is implemented as a Python class (e.g. `SAPTWorkflowManager`) which manages the lifecycle of tasks. Its responsibilities include:

- **Task Decomposition:** Taking user input and splitting into one or more SAPT calculation tasks (each defined by a pair of monomers and a set of computational parameters).
    
- **Resource Scheduling:** If running locally, use a `concurrent.futures.ProcessPoolExecutor` or `multiprocessing.Pool` to execute tasks in parallel up to the allowed number of processes. If running with Dask, connect to a Dask client and submit tasks via `client.map` or `client.submit`. The orchestrator abstracts these details so that the user simply specifies “local” or “distributed” mode.
    
- **Monitoring and Coordination:** Keep track of running tasks, collect results as they finish, and handle task dependencies (for example, if a workflow had multiple steps – though a basic SAPT calculation might not have sequential dependencies, more complex workflows could). The orchestrator can periodically check task statuses, possibly using callbacks or polling if using Dask futures. It also ensures that results are collated in the correct order and format for the user when all tasks complete.
    
- **Integration with SLURM:** In a cluster setting, the orchestrator can either submit a single Dask scheduler job and multiple worker jobs to SLURM (using Dask-jobqueue or a small wrapper that calls `sbatch`), or it can itself run on a login node and submit each SAPT task as a separate Slurm job (though the latter approach is less efficient for large numbers of tasks). The recommended strategy is to use Dask’s integration so that the orchestrator hands off tasks to Dask, and Dask handles the queuing on SLURM. This decouples our code from direct scheduler management and leverages Dask’s resilience and scheduling algorithms.
    

The orchestrator is designed to be **stateless between runs** (it doesn’t require a persistent server process like QCFractal’s server ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=Image%3A%20))), but it uses the state management layer to record progress. For example, after dispatching tasks, it may save a “checkpoint” list of which tasks completed, so if the process or node crashes, it can reload and avoid re-running successful tasks on restart.

**3. Backend Integrations (Plugins):** Each supported QC code (Psi4, CamCASP, SAPT2020) is implemented as a backend class providing a standard interface for a “SAPT calculation.” This design takes inspiration from ASE’s calculator interface, where different simulation codes can be swapped without changing the user’s workflow logic ([ASE](https://rosengroup.slite.page/p/BGJeKFLJdSPpJK/ASE#:~:text=The%20%20Atomic%20Simulation%20Environment,throughput%20calculations)) ([Atomic Simulation Environment — ASE documentation](https://wiki.fysik.dtu.dk/ase/#:~:text=ASE%20provides%20interfaces%20to%20different,many%20available%20algorithms%20in%20ASE)). In our system, we define an abstract base class like:

```python
class SAPTBackend(ABC):
    @abstractmethod
    def compute_sapt(self, molA, molB, options) -> Result:
        """Execute a SAPT calculation on monomers A and B with given options."""
```

Concrete implementations:

- **Psi4Backend:** Uses the Psi4 Python API (`psi4.core` module) to set up the dimer and monomer molecules, configure the SAPT computation (e.g. `psi4.energy('sapt0')` or appropriate calls for higher-order SAPT), and run it in-process. Because Psi4 is a Python library, this backend can directly call functions and retrieve results (e.g. interaction energy and decomposition terms) from Psi4’s outputs. We ensure thread-safety by running each Psi4 call in its own process (since Psi4 might use global resources, multiple Psi4 computations are best isolated in separate processes). The backend will translate our common `options` (like basis set, SAPT level, etc.) into Psi4-specific inputs.
    
- **CamCASPBackend:** CamCASP is an external suite of programs (with its own input file structure). This backend would take the molecular data from the user (likely geometry of monomers, charges, etc.) and **write an input file** in CamCASP format or call a CamCASP preparation script. It then executes CamCASP binaries via Python’s `subprocess` (for example, calling the SAPT(DFT) module of CamCASP). The backend waits for the external process to finish, checks its exit code, and then parses the output files to extract SAPT energy components. All these details are encapsulated so that from the orchestrator’s perspective, `CamCASPBackend.compute_sapt()` simply returns a result object or raises an exception on failure.
    
- **SAPT2020Backend:** Similarly, SAPT2020 (a codebase including many SAPT variants) likely has a command-line interface. We implement this plugin to format the required input (perhaps an input deck or a set of files with monomer wavefunctions), invoke the SAPT2020 executable, and parse its output. If SAPT2020 has a Python API or library interface, we could use that, but assuming it’s an external program, the pattern is the same as CamCASP – prepare, run, parse.
    

All backend classes will produce a **unified result data structure** (e.g. an object or dict containing total interaction energy and its decomposition into electrostatics, exchange, induction, dispersion, etc., plus any metadata like computation time). This allows the rest of the workflow to handle results uniformly. New backends can be added by simply subclassing `SAPTBackend` and registering the plugin (e.g. through a factory that chooses the backend based on a string name). This plugin model echoes AiiDA’s plugin framework for adding new calculation types easily ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=processes%2Fhour%2C%20while%20automatically%20preserving%20and,a%20flexible%20plugin%20model%20to)). It balances flexibility (extend to new codes or methods) with ease of use (user just selects a backend by name).

**4. State Management & Data Storage:** To ensure reproducibility and recovery, the system will incorporate a lightweight state management component:

- Each task (SAPT calculation) is assigned a unique ID and working directory. All input files, output files, and logs for that task are stored in that directory. For Psi4 (which might not produce an external output file when using the API), we can capture its output text and write it to a log file for record-keeping.
    
- A **task database** (could be as simple as a JSON or SQLite DB) keeps a record of all tasks in a workflow, their parameters, status, and results. This is analogous to AiiDA’s provenance graph but far simpler: essentially a table of tasks that can be queried or resumed. The state manager can load this record on startup to skip completed tasks or avoid duplicate computations. In high-throughput studies, this prevents losing days of work if a run halts unexpectedly, aligning with the best practice of persisting workflow state ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=match%20at%20L422%20only%20when,the%20engine%20will%20keep%20waiting)).
    
- Provenance information (for reproducibility) stored per task includes: input geometries of monomers, basis set and method used, backend and version (e.g. Psi4 version X.Y.Z) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=Reproducibility%20is%20one%20of%20the,Crucially%2C%20such)) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=a%20system%20should%20not%20merely,recursively%29%20their%20respective%20provenance)), any random seeds or nondeterministic parameters (usually none for SAPT), and the date/time and hostname where it was run. By capturing these, one can later exactly retrace or re-run the calculation if needed, which is essential for scientific reproducibility ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=in%20large%20amounts%20of%20interconnected,recursively%29%20their%20respective%20provenance)).
    
- The state manager also handles **resource usage data** if we choose to record it (e.g. wall time, memory used by each job). This can be valuable for performance tuning and monitoring. For example, after each task, the backend or orchestrator could query the resource usage (if available via Psi4 or system tools) and log it.
    

**5. Logging and Notification:** A logging subsystem will produce human-readable logs at both the workflow level (high-level progress messages, summary of results) and the backend level (detailed output from each calculation). In case of failures, the log will include error messages and possibly hints for resolution. For cluster runs, logs might be written to a file that can be inspected live or after the fact. Optionally, the system could notify the user (via email or messaging) when a long-running workflow completes or if it aborts, but this is an ancillary feature.

By clearly defining these components and their roles, the design ensures that each part of the system can be developed and tested in isolation. For example, backend plugins can be tested with dummy inputs to ensure they correctly call the external codes and parse outputs, independent of the orchestrator. The orchestrator can be tested with a mock backend (that just returns canned results) to verify scheduling logic. This modularity and separation of responsibilities is crucial for maintainability and extensibility.

## API Schema and Usage Example

To illustrate the user experience, below is a conceptual outline of the API and how a typical user would interact with the SAPT workflow system:

- **High-Level API:** We provide a primary class (e.g. `SAPTWorkflow`) that represents an entire calculation campaign. The user populates it with one or more SAPT tasks and then executes it. For convenience, a simpler function interface (`run_sapt`) can wrap common use cases.
    

For example, a simple Python usage might look like:

```python
from sapt_workflow import SAPTWorkflow, Molecule

# Define monomers (Molecule could be a simple dataclass with geometry & charge info)
molA = Molecule.from_xyz("monomerA.xyz")
molB = Molecule.from_xyz("monomerB.xyz")

# Create a workflow and add a SAPT calculation task
wf = SAPTWorkflow(default_backend="psi4", basis="jun-cc-pVDZ", sapt_level="SAPT0")
wf.add_calculation(molA, molB, label="A-B interaction")

# Run the workflow locally with 4 parallel processes
results = wf.run(mode="local", processes=4)
print(results["A-B interaction"].total_energy)
```

In this pseudo-code:

- `SAPTWorkflow` is initialized with default settings (which backend, basis set, SAPT level, etc., which the user can override per calculation if needed).
    
- `add_calculation` registers a task with specific monomers and gives it a label.
    
- `run()` executes all added tasks, either locally or distributed. The `results` could be a dictionary of label -> result object, or the workflow could attach results to the internal task objects.
    
- **Flexibility:** The API allows overriding defaults. For instance, one could do `wf.add_calculation(molA, molB, backend="CamCASP", sapt_level="DFT-SAPT")` to use a different backend for a specific task. This flexibility can be useful if, say, one wants to compare results between Psi4 and SAPT2020 easily by running both in one workflow.
    
- **Ease of Use:** Reasonable defaults mean a novice user doesn’t need to know all Psi4 keywords or CamCASP details. They can simply specify high-level options. The API should validate inputs (e.g., ensure the basis set is supported, ensure molecules have necessary data like charges if required) and provide clear errors if something is amiss.
    
- **Configuration File Option:** As an alternative to the Python API, users could provide a config file. For example, a YAML file listing multiple pairs of molecules and settings. The library can have a method `SAPTWorkflow.from_yaml("input.yml")` to create and run workflows. This is similar in spirit to how FireWorks or Atomate allow writing workflows in YAML for ease of use by non-developers.
    

**Schema Summary:** Internally, the core data structures might include:

- A `Task` class containing all info for one SAPT job (monomer file paths or coordinates, options, selected backend, status, result).
    
- A `Result` class capturing energies and components (electrostatics, exchange, etc.) and metadata.
    
- The `SAPTWorkflow` class holds a list of Tasks and has methods to dispatch them (possibly using different executors for local vs Dask).
    
- The `Backend` classes are mostly internal; users just specify which backend via name.
    

**Balance Between Flexibility and Usability:** The API is designed so that **common workflows require minimal code**, but power users can dip into lower levels:

- For example, the Psi4 backend could allow the user to pass a custom Psi4 input snippet or a Python function that manipulates the Psi4 `Molecule` object, for special cases not covered by defaults.
    
- We could expose a hook in `SAPTWorkflow` like `before_run(task)` or `after_run(task, result)` that advanced users can override (via subclassing) to customize behavior (e.g., to do something like modify a guess if an initial attempt fails, or to post-process results).
    
- These are optional; the primary interface remains straightforward for standard use.
    

This design echoes the philosophy of AiiDA and QCFractal: provide sensible high-level constructs for typical use, but also allow users to script custom workflows when necessary ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=This%20approach%20of%20defining%20processes,However)) ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=achieve%20its%20goals)). By making the API Pythonic and intuitive, scientists with basic Python knowledge can leverage distributed computing without needing to write boilerplate code for job submission or data parsing – the framework handles those aspects transparently.

## Backend Integration Strategy

Integrating multiple quantum chemistry packages is a core requirement. Our strategy is to isolate all code-specific logic in **backend adapter classes** and design a uniform interface as discussed. Here we detail how each integration is approached and how the system maintains a clear boundary between the workflow logic and backend specifics:

- **Psi4 (Default Backend):** Psi4’s strength is its Python integration, which we fully leverage. The Psi4 backend will use the Psi4 API to do SAPT calculations in memory. For example, given two monomer geometries, the backend will create a dimer `Molecule` in Psi4 with appropriate fragmentation, set the basis set and SAPT level (e.g. SAPT0, SAPT2+(3) etc.), and call `psi4.energy("<sapt-method>/<basis>")`. Psi4 returns energies and can provide decomposition terms via its `Wavefunction` or defined `psi4.variable` entries. The backend collects these (e.g. `psi4.variable('SAPT TOTAL ENERGY')`, and similarly for components) and constructs our `Result` object. This integration is relatively straightforward since Psi4 does the heavy lifting and Python↔C++ boundary is managed by the Psi4 library. One consideration is that Psi4 can utilize multiple threads internally for its computations. If a user requests, say, 8 SAPT jobs in parallel on an 8-core machine, each Psi4 job might need to be restricted to 1 thread to avoid oversubscription. We can handle this by setting Psi4’s `num_threads` globally or per call. The backend would expose an option for threads per job, or default to 1 when running concurrent jobs.
    
- **CamCASP:** CamCASP requires a different approach since it’s not a native Python library. The integration will rely on **file-based communication**. The CamCASP backend will have templates for input files or use CamCASP’s provided scripting interface (if any). Steps for a CamCASP SAPT(DFT) run could be: (1) generate monomer density matrices or wavefunctions (possibly by calling an electronic structure code – CamCASP might interface with DALTON or other codes, or require pre-computed monomer properties), (2) create a configuration file telling CamCASP which SAPT components to calculate, (3) run the CamCASP command-line tool, (4) parse the output text or files for energy components. This is non-trivial, so the backend will encapsulate all necessary sub-steps. It might call Psi4 or another QM code to get monomer data if CamCASP needs it (since CamCASP is more of an analysis tool). Fortunately, CamCASP is specifically designed for intermolecular interactions, so it likely has streamlined input. The backend might look like:
    

```python
class CamCASPBackend(SAPTBackend):
    def compute_sapt(self, molA, molB, options):
        inp_path = self._write_camcasp_input(molA, molB, options)
        retcode = subprocess.call(["camcasp", inp_path])
        if retcode != 0:
            raise ExecutionError("CamCASP failed with code %d" % retcode)
        out_data = self._parse_camcasp_output()
        return self._package_result(out_data)
```

Here `_write_camcasp_input` and `_parse_camcasp_output` are helper methods to handle CamCASP I/O. By structuring it this way, we ensure that the main orchestrator simply calls `CamCASPBackend.compute_sapt` and doesn’t worry about details beyond catching exceptions.

- **SAPT2020:** The SAPT2020 code suite (as indicated by literature ([Symmetry-Adapted Perturbation Theory Based on ...](https://pubs.acs.org/doi/10.1021/acs.jctc.1c00344#:~:text=Symmetry,with%20a%20rigid%20monomer))) includes many SAPT variants and likely a driver for intermolecular potential energy surfaces. We integrate it similarly to CamCASP – via external execution. We’ll gather what inputs SAPT2020 needs (perhaps a formatted file with monomer orbital info or a combined dimer file). Possibly SAPT2020 uses a format like PSI’s older SAPT codes or requires an SCF step beforehand. One integration approach is to use Psi4 for the SCF of each monomer (since we have Psi4 already) and then feed those wavefunctions into SAPT2020 if it accepts molden files or similar. Alternatively, if SAPT2020 can perform the whole SAPT calculation given coordinates and a basis, the backend will just call it directly. The parsing of SAPT2020 output will extract the energy components.
    

**Unified Results and Units:** All backends will normalize the results to a common format (e.g., energies in Hartree or kJ/mol as needed, with appropriate conversions, and similarly ensure the same components are reported if available). If a backend doesn’t support a certain piece of data (for instance, maybe CamCASP doesn’t do higher-order exchange terms that Psi4 can), the result can leave it null or give a warning. But the main fields like total energy and the primary SAPT breakdown terms will be provided for all, so that the user can compare results from different backends directly.

**Maintaining Separation:** The core system will treat backend calls as black boxes: the orchestrator doesn’t need to know _how_ CamCASP is being run or whether Psi4 uses an in-memory call – it only cares about success/failure and the returned result. This means the orchestrator can be oblivious to the differences in backend implementation. The benefit is twofold: (1) adding a new backend (say, a future “SAPT2025” code) doesn’t require changes to orchestrator logic, just writing a new plugin class; (2) we can debug and improve backend plugins independently (for example, update how we parse CamCASP outputs if a new version changes format, without touching other parts of the system).

**Testing Integration:** For each backend, we will create validation tests with known SAPT values (from literature or small system benchmarks) to ensure our integration yields correct results. This testing is crucial, since any slight mis-parsing could lead to incorrect energies. By isolating code per backend, we reduce the risk that a fix for one backend affects others.

## Parallel Execution and Task Scheduling

One of the system’s core strengths is its ability to execute multiple SAPT jobs in parallel, either on a multicore workstation or a distributed compute cluster. We employ different parallelization strategies depending on the environment, all under a common interface so the user doesn’t have to manage low-level details.

**Local Parallelism (Multiprocessing):** Python’s Global Interpreter Lock (GIL) would normally prevent true parallel threads for CPU-bound tasks, but here each SAPT task will either call an external program or perform heavy computation in native code (Psi4’s C++ backend), so using **multiprocessing** is appropriate. The orchestrator will detect the number of available cores (or use user-specified `processes` count) and launch a pool of worker processes. Each worker process executes one SAPT task at a time using a backend. This could be implemented with `multiprocessing.Pool.map` or with the higher-level `concurrent.futures.ProcessPoolExecutor` for convenience.

Key considerations for local execution:

- We will limit to e.g. 8 processes by default (as specified) to avoid oversubscription. If the user has more cores and wants to use them, it can be made configurable.
    
- If Psi4 tasks are multi-threaded, we either pin them to one core or adjust the pool size (e.g. if user wants each Psi4 to use 2 threads on an 8-core machine, we would run 4 processes * 2 threads each). The API can allow specifying threads per task.
    
- **Resource monitoring:** While processes run, the orchestrator can monitor their memory and CPU usage using something like `psutil`. If a process exceeds a memory threshold (perhaps user-specified), the system could preemptively terminate it or at least flag a warning. This is an advanced feature; at minimum we rely on the OS (or SLURM on clusters) to handle resource limits. Still, logging memory and time usage of each job is useful for users to optimize future runs.
    
- The multiprocessing approach is straightforward and has low overhead for up to O(10) tasks. Python’s overhead is negligible compared to the cost of SAPT computations, which can take minutes or hours each.
    

**Distributed Execution with Dask:** For larger scales or use on HPC clusters, we integrate **Dask Distributed**. Dask provides a flexible paradigm where a central scheduler coordinates many workers executing tasks. In our design, if `mode="distributed"` (or if the user provides a Dask `Client`), the orchestrator will:

- Connect to a Dask scheduler. This could be a scheduler running on the same machine or on a cluster head node. The user might start a Dask scheduler and workers manually, or more conveniently, we could programmatically launch a cluster using `dask_jobqueue.SLURMCluster` for SLURM environments ([Dask-Jobqueue — Dask-jobqueue 0.9.0+8.g6dc463d documentation](https://jobqueue.dask.org/#:~:text=Dask,Dask%20on%20common%20job)). For example, the system could detect a cluster environment and do something like:
    
    ```python
    from dask_jobqueue import SLURMCluster
    cluster = SLURMCluster(job_cpu=1, job_mem="4GB", cores=1, processes=1, walltime="01:00:00")
    cluster.scale(n=20)  # request 20 workers
    client = Client(cluster)
    ```
    
    This would submit 20 single-core jobs to SLURM, each running a Dask worker, effectively giving us 20 parallel workers for SAPT tasks. The specifics (memory per job, time) could be exposed via config or auto-calculated from task input size (though that’s tricky; better to leave to user or config defaults).
    
- Once a Dask client is ready, the orchestrator submits tasks to the Dask scheduler using `client.submit` for each SAPT task (or `client.map` for a batch). Each task submission includes the function to execute (which would internally call the appropriate backend’s compute method) and the data needed (monomer geometries, options). We have to ensure these data are serializable for sending to workers. Likely, simple Python objects (coordinates as lists or numpy arrays, option dicts) are fine. The backend code itself must be available on the worker – since our whole package can be installed on cluster nodes, that’s handled by environment setup.
    
- Dask will distribute these tasks to the workers (which may be on many different nodes). The workers run the tasks in parallel. Dask handles load balancing and can even work with heterogeneous task durations. If some SAPT calculations take longer (e.g. larger systems) and others finish quickly, Dask will schedule new tasks on free workers to maximize throughput. This dynamic scheduling ensures efficient use of resources.
    
- As tasks complete, the orchestrator can gather results via `future.result()` calls or using Dask callbacks. We may collect results as they come (allowing streaming of partial results) or wait for all to finish. In either case, the results are eventually aggregated and returned in a consistent format.
    

**Fault Tolerance and Scalability:** Dask is quite robust – if a worker dies or a task fails, it reports back without bringing down the whole workflow. We integrate this with our error handling (see next section) to perhaps retry tasks if appropriate. The use of Dask also allows scaling to **hundreds of tasks concurrently** if the cluster can handle it, aligning with the goal of high-throughput computing ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=QCArchive%20is%20a%20platform%20that,retrieval%20and%20analysis%2C%20or%20export)). This approach is inspired by the QCFractal model (which uses a central server and distributed workers) ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=Image%3A%20)), but we leverage Dask to avoid writing a custom scheduler. Essentially, our orchestrator + Dask is serving a role similar to AiiDA’s daemon + RabbitMQ engine or QCFractal’s server, but in a lightweight way.

**SLURM and HPC Integration:** There are a couple of ways to integrate with SLURM:

- _Via Dask (recommended):_ Use Dask-Jobqueue as described to allocate workers on the cluster. This abstracts away SLURM job submission details. We simply specify how many workers and the resources each worker needs. The advantage is that Dask can then elastically manage these jobs (we could even adaptively scale the number of workers based on workload). Many real deployments use this pattern, as it combines the comfort of Python with the control of the cluster scheduler ([Setting up a DASK cluster using dask-jobqueue](https://mom6-analysiscookbook.readthedocs.io/en/latest/notebooks/setting_up_dask_jobqueue.html#:~:text=Setting%20up%20a%20DASK%20cluster,GFDL%20users%20running%20on%20PP%2FAN)).
    
- _Direct submission:_ In some cases, the user might not want to use Dask. We could provide an alternative where each task is written out as a shell script or SLURM batch script and submitted with `sbatch`. The workflow manager would then have to poll SLURM for job completion or use job dependencies. This is essentially re-implementing what Dask offers, so it’s optional. If implemented, we would have a component (perhaps an `SlurmJobExecutor`) that takes a Task, writes a job script (loading necessary modules, running the backend via a command-line call, etc.), and submits it. It would need to record the job ID and periodically check job status (via `squeue` or SLURM Python APIs). Once the job finishes, the executor would collect the output files and mark the task complete. This mode is more complex to implement and error-prone, so we’d suggest using it only if Dask is not available. Still, having a basic SLURM submission capability could be useful for very large single jobs or if Dask overhead is an issue.
    

**Parallel Efficiency:** We anticipate that SAPT tasks are relatively heavy (minutes to hours each), so the overhead of using multiprocessing or Dask is negligible. Communication overhead (sending inputs/results) is small compared to computation. Thus, the system should scale well. If a user runs 100 SAPT jobs on 10 nodes with 40 cores total, we expect nearly 100% utilization. The design also allows _task-level parallelism_ as well as potential _intra-task parallelism_ (e.g. if a single SAPT calculation could be parallelized with MPI or threads, which some codes support). In the latter case, the user would likely request fewer simultaneous tasks, each using multiple cores. Our resource management should accommodate that (for example, by specifying per-task CPU and memory needs, and scheduling accordingly – Dask allows specifying resource tags or memory limits per task).

**Resource Monitoring and Load Balancing:** Dask provides a dashboard that can show task progress and memory use on each worker. For local runs, we can integrate simple monitoring: for instance, print a progress bar or percentage of tasks done, and maybe the average time per task. On clusters, users can consult Dask’s web UI for a detailed view. The system could also output periodic summaries (e.g. “X out of Y tasks completed, longest task running for Z minutes so far”). This helps users trust that the computation is progressing (important for long runs). For dynamic load balancing, Dask inherently moves tasks from busy workers to idle ones. Our system doesn’t need its own load balancer thanks to that.

By supporting these parallel execution modes under one roof, the workflow system can be deployed in various scenarios: a researcher’s laptop (multiprocessing), a shared lab server (still multiprocessing or a local Dask cluster), or a supercomputing environment (Dask+SLURM with many workers). The user interface to choose these is as simple as a parameter in the API or config. Internally, the orchestrator abstracts the differences so that other components (backends, etc.) do not need to change based on execution mode – they just execute when called.

## Error Handling Strategies for High-Throughput Workflows

Error handling is a critical aspect of any automated computational workflow. In high-throughput SAPT calculations, failures can and will occur – perhaps a particular dimer fails to converge, or an external program crashes on an edge-case input. The workflow system must handle such errors _gracefully_ and _robustly_, so that one failure does not derail the entire set of calculations. Here we outline the error handling patterns and features recommended for this system:

**1. Granular Try/Except Wrapping:** Each individual task execution (e.g., a call to `backend.compute_sapt`) is wrapped in a try/except block within the worker process (or within the task function if using Dask). This means if a SAPT job raises an exception, we catch it at the task level. The error (exception message, traceback, or external process exit code) is then reported back to the orchestrator rather than propagating uncaught. The orchestrator can mark that task as **failed** but continue with others. This way, 100 calculations can proceed even if 5 of them encounter errors – those 5 will simply result in error reports, not a full stop. This approach is standard in workflow managers to maximize throughput and not lose partially completed work due to a few bad apples ([Open Chemistry, JupyterLab , REST , and quantum chemistry (Journal Article) | NSF PAGES](https://par.nsf.gov/biblio/10453965-open-chemistry-jupyterlab-rest-quantum-chemistry#:~:text=property%20data%20while%20also%20enabling,Overall)).

**2. Logging and Classifying Errors:** When an error occurs, the system logs detailed information. For external codes, the stderr/stdout of the process is captured. Common error types include: SCF convergence failure, missing/bad initial guess, basis set not supported, segmentation fault, exceeding memory, etc. The system can **classify** errors by inspecting output. For example, if Psi4 throws an exception for non-convergence, the backend can catch that specific exception type (Psi4 likely raises a `RuntimeError` with a message). For CamCASP or SAPT2020, we might scan the text output for keywords like “ERROR” or known phrases (“failed to converge”, “segfault”, etc.). By classifying, we can implement targeted handling: e.g., if it’s a convergence error, perhaps try again with a different algorithm or loosened criteria, whereas if it’s a file not found, that might indicate a setup bug and we skip retry.

**3. Automated Retry and Recovery:** Taking inspiration from other tools (like Q-Chem’s QCORR module in QChASM, which automatically handles convergence issues and resubmits jobs ([Open Chemistry, JupyterLab , REST , and quantum chemistry (Journal Article) | NSF PAGES](https://par.nsf.gov/biblio/10453965-open-chemistry-jupyterlab-rest-quantum-chemistry#:~:text=property%20data%20while%20also%20enabling,Overall))), we can implement some automated recovery:

- **Retry with Adjustments:** For SCF convergence failures, the system could attempt a second try with a better initial guess or a different SCF solver if the backend supports it. For example, Psi4 could switch to DIIS off or alter damping on a retry. These strategies would be coded into the Psi4Backend as an internal loop: try once, if fails and error is SCF, adjust and try again. We limit the number of retries (say 1 or 2) to avoid infinite loops.
    
- **Fallback to Different Backend:** In some cases, if one code fails on a particular system, another might succeed. We could provide an option (if the user enables it) to fall back – e.g., if Psi4 fails on a complex dimer, try SAPT2020 for that one. This might not always be practical due to differences in methods, but it’s conceivable.
    
- **Job Resubmission:** In a cluster scenario, if a worker node dies or a job is killed (perhaps due to time limit), Dask can indicate the task as lost. The orchestrator could then resubmit that task either to Dask again or, if using direct Slurm, submit it anew. This is more advanced, but Dask often can be configured to retry X times automatically. We should allow at least one automatic retry of a task on a fresh worker in case of transient errors or node issues.
    

**4. Workflow-Level Error Policies:** The system should let the user decide what to do on errors. Possible policies: continue on error (default), stop on first error (if the user wants to troubleshoot interactively), or continue but limit retries. These can be set in the configuration. By default, we _continue through errors_, recording them for later review, since the aim is to complete as many calculations as possible (a principle of high-throughput computing). A summary at the end can list how many succeeded vs failed.

**5. Detailed Reporting:** Each failed task should produce a concise error report, including: task ID or label, which backend was used, a summary of the error (e.g. “Psi4 SCF did not converge in 150 iterations”), and the location of detailed logs or outputs for debugging. This could be written to a “errors.log” file and also be part of the returned results (e.g. result object might have an `.error` attribute or we return a list of errors). The idea is to help the user quickly identify and fix issues in their input or in the codes.

**6. Safe Termination and Cleanup:** If a fatal error occurs (something truly unexpected that forces stop, or user interrupts), the system should attempt a clean shutdown: terminate any running subprocesses or Dask jobs, close files, and save the current state. This prevents orphan processes or temporary files left on the cluster. Using context managers or signal handlers can help intercept `KeyboardInterrupt` or SIGTERM to do this cleanup.

**7. Testing Error Scenarios:** We will simulate common failure modes to ensure our handlers work. For example, provide an intentionally impossible molecule to trigger SCF failure and see that the workflow continues. Also test network disruptions in distributed mode (maybe kill a Dask worker to see that tasks are retried on another).

Implementing these error handling measures draws on best practices from existing systems: AiiDA emphasizes advanced error handling in workflows (including the ability to respond to errors in workflow logic) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=processes%2Fhour%2C%20while%20automatically%20preserving%20and,a%20flexible%20plugin%20model%20to)), and QChASM’s tools explicitly built automated error correction for quantum chemistry tasks ([Open Chemistry, JupyterLab , REST , and quantum chemistry (Journal Article) | NSF PAGES](https://par.nsf.gov/biblio/10453965-open-chemistry-jupyterlab-rest-quantum-chemistry#:~:text=property%20data%20while%20also%20enabling,Overall)). By incorporating similar patterns (classification of errors and automated fixes), our SAPT workflow system will be highly robust for long runs. Users can trust that if an error is recoverable, the system will try to recover; if not, it will isolate the failure and not lose all other results. This is essential when running hundreds of expensive calculations overnight or on a remote supercomputer.

## Provenance, State Management, and Reproducibility

In computational science, _reproducibility_ is paramount ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=Reproducibility%20is%20one%20of%20the,Crucially%2C%20such)). The system should enable users (and reviewers) to retrace every result to the exact inputs and processes that produced it. Moreover, managing the state of a large workflow (with potentially thousands of calculations) is crucial to avoid duplicating work and to allow stopping/resuming. We adopt several strategies for provenance and state management:

**1. Automatic Provenance Tracking:** Every calculation’s **inputs, outputs, and metadata** are recorded. This echoes AiiDA’s philosophy of storing the full graph of processes and data ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=match%20at%20L486%20the%20execution,in%20turn%20be%20used%20as)), though we implement it in a simpler form. For each SAPT task, we store:

- The input molecular structures (we can store a copy of the XYZ or a unique identifier if the molecule is reused).
    
- The computational parameters (method, basis, any auxiliary options).
    
- The backend and version used (e.g. Psi4 1.5, CamCASP 6.0).
    
- The output results (energies, etc.) and output files or logs.
    

All this can be organized in a directory structure or a database. A simple yet effective approach: have a main **results folder** with a subfolder for each task (named by task ID or a descriptive name). Inside each task folder: an input file (perhaps a JSON containing all input info), the raw output (log file or parsed results), and any intermediate files (like monomer wavefunctions, etc., if needed). The system could also produce a consolidated CSV or JSON summary listing each task and its result for quick access.

**2. Unique Identifiers and Hashing:** We can generate a unique hash based on the content of a task’s input (geometries + method). This could serve as a key in a database to avoid re-running identical tasks. For example, if a user accidentally submits the same pair twice, we could detect it and skip or use cached result. (This is similar to how some workflow tools do caching of computations by hashing inputs). Even if we don’t automatically skip, we can warn the user of duplicates.

**3. Checkpointing and Resumption:** The state manager will periodically save the workflow state (list of completed tasks, currently running tasks). If the orchestrator process ends (crash or intentionally stopped), the user should be able to restart the workflow and not lose progress ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=match%20at%20L422%20only%20when,the%20engine%20will%20keep%20waiting)). For instance, a `SAPTWorkflow` could be saved to disk (pickle or JSON) after each task finishes. A resume method would reload this, check which tasks are done (perhaps verify their output files exist), and then continue with the rest. This is invaluable for long runs on clusters where wall-time limits might require splitting the run across multiple submissions. Instead of manually tracking what was done, the system does it.

**4. Verification of Outputs:** As part of state management, after a task completes and its output is parsed, we can do a quick sanity check – e.g., verify that the sum of SAPT components equals the total energy within a tolerance (this can catch parsing errors or incomplete runs). Also, if any component is `None` or missing (which might indicate the code didn’t produce it), mark that in the result. This way we ensure the stored results are self-consistent and complete.

**5. Reproducibility and FAIR Data:** The data recorded by the system should be sufficient for another researcher to reproduce the calculation. This aligns with FAIR (Findable, Accessible, Interoperable, Reproducible) principles ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=robust%20workflows,in%20the%20AiiDA%20informatics%20infrastructure7)). In practice, this means if someone has the same quantum chemistry codes installed, they could take the recorded input (geometry, method, etc.) and get the same output. By storing the exact version of the code and any relevant environment info (e.g., if Psi4’s results depend on the specific version, which they can ([SAPT: Symmetry-Adapted Perturbation Theory](https://psicode.org/psi4manual/master/sapt.html#:~:text=Caution)) ([SAPT: Symmetry-Adapted Perturbation Theory](https://psicode.org/psi4manual/master/sapt.html#:~:text=May%202022%20c,The%20reasoning%20and%20reward)), we note the version), we inform the user if results might differ on a different version. Optionally, the system can store the environment’s Python package list or a conda environment file for full reproducibility. This might be overkill for everyday use, but it’s useful for archival of important results.

**6. Lightweight Database (Optional):** For quick querying of results and tracking, we could use a SQLite database. Each task’s data can be inserted as a row when completed. This allows users to run SQL queries like “select * from results where total_energy < -5 kcal/mol” to filter interesting cases, for example. It also helps in generating summaries or doing analysis on the fly without having to open each file. However, we must ensure writing to the DB is thread-safe with multiple workers (could queue writes through the orchestrator). A simpler approach is to gather everything at end and then write the DB once.

**7. Provenance Graph (Advanced):** If we ever compose multi-step workflows (where one step’s output is another’s input), tracking the dependency graph is important. For now, a single SAPT calc doesn’t have such internal dependencies (besides monomer SCFs which are done within the same task typically). If in future we had workflows like “optimize monomers -> then do SAPT”, we would incorporate provenance links (monomer opt data used in SAPT). AiiDA’s design of a directed acyclic graph of data nodes and process nodes ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=the%20execution%20of%20processes%2C%20along,in%20turn%20be%20used%20as)) is a reference model – our system can implement a simplified version by storing references to input data for each task.

In summary, the state and provenance management will ensure that users can **trust the integrity of their results** and have a trail to follow for validation. By automatically collecting this information, we remove the burden from users to manually organize files or note down what was run. This is especially beneficial in high-throughput studies where manual record-keeping is not feasible for hundreds of calculations. Our approach may not be as fully fledged as AiiDA’s provenance database, but it covers the essential aspects of reproducibility while remaining relatively light and easy to implement.

## Leveraging Best Practices from Existing Workflow Systems

We have drawn inspiration from established scientific workflow frameworks to inform this design. Here we highlight key architectural best practices from AiiDA, ASE, and QCFractal (QCArchive) and how they influence our system:

- **AiiDA (Automated Interactive Infrastructure for Database Applications):** AiiDA is known for its rigorous provenance tracking, plugin system, and HPC workflow management ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=should%20be%20generic%20enough%20to,implemented%20in%20the%20AiiDA%20informatics)) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=match%20at%20L486%20the%20execution,in%20turn%20be%20used%20as)). From AiiDA, we adopt the idea of **separating the workflow logic from the execution of external codes** via a plugin interface. AiiDA’s “calculations” vs “workflows” abstraction ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=run%20by%20the%20engine%2C%20is,output%2C%20given%20certain%20data%20as)) taught us to distinguish between the actual computation (SAPT calculation which generates data) and the orchestration (our `SAPTWorkflow` which doesn’t generate new data itself but coordinates calculations). We also mirror AiiDA’s **resilience and state persistence**: AiiDA’s engine persists state to a database so workflows can resume after crashes ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=match%20at%20L422%20only%20when,the%20engine%20will%20keep%20waiting)), and we implemented a checkpoint/resume mechanism to similar effect. While we do not implement a full database of nodes and links, we ensure that all inputs/outputs are saved and linked, providing a provenance trail (a lighter-weight analog of AiiDA’s graph). Additionally, AiiDA’s **error handling** influenced our design – it provides hooks to handle errors and even automate certain responses, guiding our approach to retries and error categorization ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=subprocesses%2C%20but%20this%20quickly%20becomes,job%20schedulers%2C%20and%20work%20chains)) ([AiiDA 1.0, a scalable computational infrastructure for automated reproducible workflows and data provenance | Scientific Data](https://www.nature.com/articles/s41597-020-00638-4#:~:text=processes%2Fhour%2C%20while%20automatically%20preserving%20and,a%20flexible%20plugin%20model%20to)). Finally, AiiDA’s plugin system for new codes encouraged us to make backends modular and easy to extend.
    
- **ASE (Atomic Simulation Environment):** ASE demonstrated the power of a **common API for different simulation codes** ([ASE](https://rosengroup.slite.page/p/BGJeKFLJdSPpJK/ASE#:~:text=The%20%20Atomic%20Simulation%20Environment,throughput%20calculations)). Its `Calculator` interface allows a user to swap, say, VASP for QE or GPAW with minimal changes to their script. We similarly enforce that all backends conform to the `SAPTBackend` interface so that, for example, switching from Psi4 to SAPT2020 is just a matter of changing a parameter. ASE’s design is also very lightweight and Pythonic, which we emulate in our user API. We aim for our `SAPTWorkflow` and related classes to feel as intuitive as ASE’s `Atoms` and `Calculator` usage. Another takeaway from ASE is the importance of **simplicity** – ASE doesn’t inherently handle workflow persistence or complex scheduling (it relies on the user or other tools for that), keeping the library focused and easy to hack. In our system, we maintain simplicity by not over-engineering the database aspect – plain files and straightforward data structures are used unless complexity demands more. This makes it easier for users to inspect and understand what the code is doing.
    
- **QCFractal / QCArchive:** QCFractal (part of MolSSI’s QCArchive) is a specialized workflow system for quantum chemistry that can manage _massive_ numbers of calculations with a client-server model ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=QCArchive%20is%20a%20platform%20that,retrieval%20and%20analysis%2C%20or%20export)) ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=Image%3A%20)). From QCFractal, we borrow the idea of a **distributed worker pool** and using a central controller. In our case, Dask serves as the distributed runtime and our orchestrator is analogous to QCFractal’s server (though ours is not persistent or database-backed). QCFractal emphasizes making distributed computing accessible to chemists without deep knowledge of it ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=achieve%20its%20goals)); likewise, we hide the Dask/SLURM details behind simple API calls so that running on a cluster is as easy as `mode="distributed"`. QCFractal also taught us about **scalability and error tolerance**: it’s built to handle thousands to millions of tasks, so it must handle node failures gracefully and store results efficiently ([QCArchive Overview — QCArchive documentation](https://docs.qcarchive.molssi.org/overview/index.html#:~:text=This%20complexity%20increase%20is%20due,number%20of%20computations%20scale%20up)). While our scale may be smaller, we still incorporate robust error handling and efficient scheduling to scale up to the hundreds or low-thousands of tasks range. Another concept is QCFractal’s use of a **database to store results for later analysis and sharing** – we similarly allow exporting results to a database or at least a structured file so that results can be later queried or shared, although we don’t require a dedicated server.
    

In summary, AiiDA contributed ideas on provenance and HPC workflow robustness, ASE contributed the common-interface and ease-of-use philosophy, and QCFractal contributed the distributed scaling and user-friendly HPC integration. By blending these best practices, our SAPT workflow system achieves a balance: _the rigorousness and scalability of a heavyweight workflow manager, with the simplicity and flexibility of a lightweight Python library_. This means users get a tool that is powerful enough for high-throughput research, yet not burdensome to learn or deploy.

## Extensibility and Future Growth

The proposed architecture is designed with extensibility in mind so that it can adapt to new requirements and technologies without major rewrites. Several facets of extensibility are considered:

- **Adding New Backends or Methods:** As new quantum chemistry programs or SAPT variants become available, they can be integrated by writing a new backend plugin. The clean interface for backends ensures this is a **contained development** – one only needs to implement the `compute_sapt` (and any helper methods for I/O) for the new code. The plugin can be distributed separately (for example, if someone writes a plugin for a proprietary code, they could maintain it outside the main project). The workflow manager can dynamically discover and load backend plugins (using entry points or a plugin registry), similar to how AiiDA and ASE allow external contributions. This modularity ensures the system stays up-to-date with minimal changes to core code.
    
- **Support for Other Workflows:** While the current focus is SAPT calculations, the architecture could be extended to other types of computations or multi-step workflows. For instance, one might want to do a **counterpoise-corrected SAPT** or a **scan of interaction energies vs distance**. Our design can accommodate this: the orchestrator could be extended to have multiple step types, or a new orchestrator subclass could be created for a sequence (e.g. a WorkChain that first calls an optimization then a SAPT calculation). The key is our separation of duties – we could reuse the backend layer for the heavy computations and just add new logic in the orchestration layer for new workflows. If, say, we wanted to integrate supermolecular calculations for comparison, we could add a new backend or a new function in the API. The user configuration can also be extended (for example, adding an option `counterpoise=True` which the Psi4 backend would interpret accordingly). Because we use dataclasses or dicts for options, adding a new field doesn’t break existing code.
    
- **Scalability Enhancements:** In the future, if we need to scale to _very large_ numbers of tasks (e.g. tens of thousands), we might consider more persistent workflow management (like having a database and a daemon process, akin to AiiDA’s daemon or a QCFractal server). Our current design could evolve by plugging in a database-backed executor or by interfacing with an existing server. For example, we could allow the option to submit tasks to a QCFractal server if one is available, instead of running them directly. This kind of extensibility means our system could interoperate with bigger ecosystems if needed. However, unless the use case demands it, the current architecture (with Dask) already handles a lot of scale and resilience.
    
- **User Interface Extensions:** We plan for a Python API primarily, but the design doesn’t preclude adding a command-line interface or a GUI. For instance, a simple CLI could parse input files and call the same `SAPTWorkflow` underneath. Since the orchestrator and backends are decoupled from the interface, building a REST API or web interface (where users submit jobs via a web form and the server runs the workflow) would be feasible without changes in the core logic. This could be a future direction for deploying the tool as a service for a community.
    
- **Maintenance and Testing:** The modular design is friendly to testing (as discussed) and maintenance. When quantum chemistry codes update (Psi4 v.next, etc.), only the corresponding backend may need updates. The system can also be extended to support new HPC resource managers (if not using Dask, one could integrate AWS Batch or other cloud systems similarly by writing a new executor class, for example). The code structure (with clear modules: `api.py`, `orchestrator.py`, `backends/psi4.py`, etc.) will be documented so that developers can quickly find where to make changes for any extension.
    
- **Performance Tuning:** If performance bottlenecks are found (for example, if JSON serialization to send tasks to Dask becomes an issue for very large molecules), we can optimize that part without affecting others. The use of efficient data formats (maybe using numpy arrays, or even binary formats for geometries) could be slotted in as needed. We keep such optimizations in mind but they don’t change the architecture.
    

In essence, the system is built not just to solve the immediate problem of SAPT workflow automation, but to serve as a **foundation for automating other quantum chemistry workflows** as well. Its extensible plugin architecture and modular design ensure longevity. By following solid software engineering principles and learning from existing platforms, we create a blueprint that will remain relevant and can grow with the user’s needs and the evolving computational chemistry landscape.
