

# SCF Convergence Failures in Psi4 SAPT(DFT) Workflows: Common Issues and Solutions

## Overview and Taxonomy of Common Failure Modes

Psi4’s SAPT (Symmetry-Adapted Perturbation Theory) workflows – especially SAPT0 and SAPT(DFT) – can encounter several recurring failure modes, particularly for challenging closed-shell systems. Based on user reports, forum discussions, and developer insights, the most common issues fall into four broad categories:

- **SCF Convergence Failures:** The monomer self-consistent field (SCF) calculations (Hartree–Fock or Kohn–Sham DFT) fail to converge or converge to an unstable solution.
    
- **Memory and Disk Allocation Errors:** The calculation runs out of allocated memory or scratch disk space, often indicated by PSI4 I/O errors or “not enough memory” exceptions.
    
- **Basis Set or Compatibility Issues:** Problems arising from the choice of basis sets – e.g. diffuse function linear dependencies, missing auxiliary bases, or effective core potentials – that can destabilize SCF or the SAPT solver.
    
- **Geometry-Induced Instabilities:** Unphysical or highly strained molecular geometries leading to numerical instabilities (e.g. SCF oscillations) despite the system being formally closed-shell.

## SCF Convergence Failures in SAPT Monomers

**Underlying causes:** When you request an SAPT calculation (e.g. `energy('sapt0')` or `energy('sapt(dft)')` in Psi4), the program must first compute SCF wavefunctions for each monomer (either Hartree–Fock or DFT, depending on the SAPT variant). These SCF cycles sometimes fail to converge, especially for large or delicate systems. Common causes include a poor initial electron density guess, oscillatory behavior in the SCF updates, or the presence of nearly degenerate orbitals that confuse the SCF procedure ([SCF guess read ---fresh man - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-guess-read-fresh-man/1479#:~:text=hokru%20%20July%2024%2C%202019%2C,2%3A57pm%20%204)) ([SCF guess read ---fresh man - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-guess-read-fresh-man/1479#:~:text=The%20large%20oscillations%20indicate%20that,Or%20a%20difficult%20electronic%20state)). In one forum case, a user saw “large oscillations” in the SCF for a SAPT0 calculation, prompting a developer to suspect either a problematic geometry or a “difficult electronic state” for the monomer ([SCF guess read ---fresh man - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-guess-read-fresh-man/1479#:~:text=The%20large%20oscillations%20indicate%20that,Or%20a%20difficult%20electronic%20state)).

Another scenario is when the SCF _does_ formally converge, but to the _wrong solution_ (a local SCF minimum that is not the true ground state). This often manifests in SAPT as a mysterious failure or unphysical result. For example, the SAPT code might print an error about a matrix not being positive-definite. In an open-shell SAPT0 example, Psi4 raised a `"Matrix is not SPD"` error, which developers explained **“indicates that the orbital hessian has a negative eigenvalue, i.e. the SCF did not converge on a minimum.”** ([SAPT: Matrix is not SPD · Issue #1682 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1682#:~:text=Hello%20everyone%2C%20So%20this%20is,the%20correct%20solution%20to%20SAPT)). In closed-shell cases, one might not get an explicit error, but an unstable Hartree–Fock solution (e.g. triplet instability of an RHF wavefunction) could lead to incorrect SAPT energy components. It’s crucial in such cases to ensure the SCF yields the _lowest-energy, stable_ orbitals for each monomer before proceeding with SAPT.

**Recovery strategies:** If a monomer SCF is stubborn, several techniques can improve convergence:

- **Switch the initial guess:** Psi4’s default SCF guess is usually `SAD` (superposition of atomic densities), which is often good, but for tough cases you can try others like `GUESS HUCKEL` or even a `"BASIS_GUESS"` projection. In one SAPT0 instability investigation, developers found that a SAD guess converged the SCF in 17 iterations but led to a saddle-point solution, whereas a Huckel guess converged in 18 iterations to a stable solution ([UHF-SAPT0 instability · Issue #1747 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1747#:~:text=susilehtola%20%20%20commented%20,79)). It’s easy to test in Psi4:
    
    ```python
    set guess huckel
    energy('sapt0', molecule=dimer)
    ```
    
    or, to use a small basis projection:
    
    ```python
    set basis_guess true          # use default small basis (e.g. 3-21G) for initial SCF
    set df_basis_guess true       # (optional) density-fit the guess for speed
    energy('sapt0')
    ```
    
    Projected basis guesses can help “bootstrap” the SCF with a simpler wavefunction and have been reported to solve some convergence problems in SAPT workflows.
    
- **Damping and DIIS settings:** Damping mixes each new SCF iteration’s Fock matrix with a fraction of the previous iteration’s Fock matrix to quench oscillations. Psi4 allows a damping percentage (`set damping_percentage <val>`) – e.g. 20–40% – and in fact **“recommends to leave damping on until convergence”** ([SCF](https://psicode.org/psi4manual/master/autodir_options_c/module__scf.html#:~:text=,18)). Users have found that adding damping often stabilizes SCF oscillations. For instance, in a SAPT0 case that initially would not converge, a user set `damping_percentage 40` and saw the SCF proceed further (though in that particular case it still oscillated around convergence) ([SCF doesn't convergence - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-doesnt-convergence/1821#:~:text=%40DF,07%20DIIS%2FDAMP%3D40)). Damping may slow the rate of convergence per iteration, but it prevents divergent swings, giving DIIS (the default convergence accelerator) a chance to work.
    
- **Level shifting:** This technique raises the energy of virtual orbitals during SCF, reducing mixing with occupied orbitals ([HF: Hartree–Fock Theory](https://psicode.org/psi4manual/1.5.0/scf#:~:text=A%20commonly%20used%20alternative%20to,DIIS%20error%20is%20smaller%20than)). Level shifting can _guarantee_ convergence if the shift is large enough, at the cost of slower convergence and the risk of converging to a higher-energy solution if over-used ([HF: Hartree–Fock Theory](https://psicode.org/psi4manual/1.5.0/scf#:~:text=unoccupied%20orbitals%20up%20in%20energy,2%2C%20respectively)). In practice, one might apply a moderate shift (e.g. 5–10 Hartree) until the density is nearly converged, then remove it. In Psi4, for example:
    
    ```python
    set level_shift 5.0
    set level_shift_cutoff 1e-2   # turn off level shift when DIIS error < 1e-2
    energy('hf')  # for monomer
    ```
    
    This approach is analogous to what other quantum chemistry programs (Molpro, CFOUR, etc.) do for tough SCF cases – it’s a transferable strategy for Psi4 as well. As the documentation notes, _“level shifting is most useful in the initial phase … enough for DIIS to work well”_ ([HF: Hartree–Fock Theory](https://psicode.org/psi4manual/1.5.0/scf#:~:text=unoccupied%20orbitals%20up%20in%20energy,2%2C%20respectively)).
    
- **Second-Order SCF (SOSCF):** Enabling `soscf true` switches to a Newton-Raphson SCF solver (which uses an approximate Hessian to converge the orbitals). SOSCF can be very effective for difficult cases because it directly iterates the orbital rotation parameters. On the Psi4 forums, users reported mixed outcomes: one user found that turning on SOSCF helped a previously diverging SAPT0 case to progress further ([SCF doesn't convergence - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-doesnt-convergence/1821#:~:text=Update%20I%20tried%20the%20soscf%2C,on%3F%20Really%20appreciate%20your%20help)), while another case reported that SOSCF converged the monomer SCF but then the calculation “suddenly stopped without any error” during SAPT proper ([SCF doesn't convergence - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-doesnt-convergence/1821#:~:text=sun%20%20June%2011%2C%202020%2C,7%3A43am%20%205)). This suggests SOSCF fixed the SCF but perhaps ran into another issue (likely an unstable solution; see below). In general, SOSCF tends to use more memory and CPU per iteration (since it solves linear equations to update orbitals), but if it converges in far fewer iterations it can save time overall. It’s worth trying for SAPT monomers:
    
    ```python
    set soscf true
    set soscf_max_iter 30
    energy('sapt0')
    ```
    
    _Trade-off:_ SOSCF’s overhead is usually acceptable for small to medium systems. For very large systems, it might be too slow or memory-heavy, in which case using DIIS with damping or level shifts is preferable.
    
- **Increase MAXITER or multi-stage approach:** Simply allowing more iterations (`set maxiter 200` or higher) may solve some cases of “slow” convergence. However, if an SCF is stagnating (e.g. oscillating between two solutions), more iterations won’t help by itself. A better approach is a **multi-stage SCF:** for example, run 50 iterations with heavy damping or a large level shift, then another 50 with those turned off, etc. Psi4 doesn’t automate this, but one can do it via the Python API: run an SCF with certain options, grab the wavefunction, then feed it in for another SCF. This gives fine control, akin to what one might do manually in other codes.
    
- **Ensure a stable solution:** After an SCF converges, especially if the system was tricky, it’s wise to check SCF stability. Psi4’s `stability_analysis` can test if the converged wavefunction is a minimum. If not, following the unstable mode can yield the correct solution ([SAPT: Matrix is not SPD · Issue #1682 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1682#:~:text=We%20now%20have%20a%20reproducible,SAPT%20completes%20with%20no%20problems)). In an example from the Psi4 issue tracker, adding a stability follow step resolved the `"Matrix is not SPD"` error and allowed SAPT to complete normally ([SAPT: Matrix is not SPD · Issue #1682 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1682#:~:text=We%20now%20have%20a%20reproducible,SAPT%20completes%20with%20no%20problems)). For closed-shell cases, one might encounter a similar need if the RHF solution has a spin-instability; the remedy is to allow an unrestricted (UHF) calculation or a stability follow to get the proper broken-symmetry solution before SAPT.
    

**Success rates and examples:** Many users have reported success by combining the above tactics. For instance, one Psi4 developer advises for UHF-SAPT: _“UHF calculations might need manual massaging… Try different guesses, add damping, use SOSCF, etc. in various combinations.”_ ([UHF-SAPT0 instability · Issue #1747 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1747#:~:text=calculations%20might%20need%20manual%20massaging)). They emphasize confirming the SCF is truly at a minimum via stability analysis. In practice, simply changing the initial guess or turning on damping often works for closed-shell systems. In one forum thread, a user’s SAPT0 calculation wouldn’t converge with default settings; by capping the monomers’ dangling bonds (fixing the geometry issue) and using a standard guess, the SCF then converged easily ([SCF doesn't convergence - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-doesnt-convergence/1821#:~:text=As%20I%20said%20in%20the,sheet%20to%20reduce%20edge%20effects)). This highlights that SCF convergence sometimes hinges on chemically sound inputs just as much as numerical tricks.

Finally, if Psi4’s SCF still struggles, an outside-the-box solution (inspired by older SAPT workflows like SAPT2020) is to perform the monomer SCF in a different program or in a separate Psi4 run, then import those orbitals. Traditional SAPT codes often rely on external SCF solutions – for example, one could run a monomer HF in Molpro (which has very robust SCF algorithms) or Q-Chem, and then feed the orbitals into Psi4. Psi4 can’t directly read all foreign orbital files, but one can output a Molden or .fchk and use `guess read` if converted to Psi4 format. In fact, Psi4’s forum confirms you can pass a **wavefunction object** to SAPT: _“you should be able to pass an SCF wavefunction as the `ref_wfn` argument for the energy call”_ ([Save orbitals and restart SCF - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/save-orbitals-and-restart-scf/1340#:~:text=We%20recently%20changed%20file%20180%2C,surprised%20to%20see%20it%20undocumented)). Using the Python API, one could do:

```python
# Pre-converge monomers separately
monA = psi4.geometry("molecule monA { ... }")
monB = psi4.geometry("molecule monB { ... }")
E_A, wfn_A = psi4.energy('hf', molecule=monA, return_wfn=True)
E_B, wfn_B = psi4.energy('hf', molecule=monB, return_wfn=True)

# Use those SCF wavefunctions for SAPT
psi4.energy('sapt0', ref_wfn=(wfn_A, wfn_B))
```

This approach gives you maximal control (you could even use different programs to get wfn_A and wfn_B if formatted appropriately). It mirrors the methodology in SAPT2020 where monomer orbitals are supplied by the user, thus bypassing any Psi4 SCF quirks for particularly troublesome cases.

## Memory and Disk Allocation Issues

SAPT calculations – especially beyond SAPT0 – can be **very demanding in memory and disk usage**. Even SAPT0 with moderately large dimers (hundreds of basis functions per monomer) will generate many two-electron integrals and intermediate matrices. If Psi4 runs out of the memory you allocated or cannot write enough data to disk, the job will crash with errors.

**Symptoms and causes:** A common error is `Fatal Error: Not enough memory` or a `PSIO Error` indicating a failure to write/read from disk. For example, one user running SAPT on a modest system (water-ethane) encountered:

```
Fatal Error: Not enough memory 
Error occurred in ... sapt2p3.cc on line: 219 ([SAPT Memory Problem - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-memory-problem/1013#:~:text=,int)) ([SAPT Memory Problem - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-memory-problem/1013#:~:text=,recent%205%20function%20calls%20were)) 
```

This was puzzling because the user’s machine had 128 GB of RAM free, yet Psi4 estimated needing only ~1 GB for the job ([SAPT Memory Problem - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-memory-problem/1013#:~:text=The%20troubling%20thing%20is%20that,900%20gigabytes)). In that case the likely culprit was that Psi4’s default **scratch directory** was running out of space or otherwise inaccessible. Indeed, another user hit a similar `PSIO Error` during an sSAPT0 job that ran ~6 days before crashing ([sSAPT0 issues: out of disk - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/ssapt0-issues-out-of-disk/1603#:~:text=Traceback%20,kwargs%29%20File%20%E2%80%9C%2Fhome%2FAridea%2Fpsi4conda%2Flib%2F%2Fpython3.6%2Fsite)) ([sSAPT0 issues: out of disk - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/ssapt0-issues-out-of-disk/1603#:~:text=RuntimeError%3A%20Fatal%20Error%3A%20PSIO%20Error,recent%205%20function%20calls%20were)). The error message `PSIO Error` with a unit number and “WRITE failed” usually means the attempt to write to scratch disk failed (I/O error or no space) ([molecular interactions - PSI4 SAPT calculation: failure to write - Matter Modeling Stack Exchange](https://mattermodeling.stackexchange.com/questions/11159/psi4-sapt-calculation-failure-to-write#:~:text=PSIO_ERROR%3A%20unit%20%3D%2097%2C%20errval,error%20writing%20to%20file)) ([molecular interactions - PSI4 SAPT calculation: failure to write - Matter Modeling Stack Exchange](https://mattermodeling.stackexchange.com/questions/11159/psi4-sapt-calculation-failure-to-write#:~:text=Error%20writing%20a%20full%20page%2C,error%20writing%20to%20file)). By default, Psi4 writes scratch files to `/tmp` unless `PSI_SCRATCH` is set, which on clusters or some systems can be a very small partition ([sSAPT0 issues: out of disk - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/ssapt0-issues-out-of-disk/1603#:~:text=Another%20common%20problem%20is%20failing,these%20files%20over%20the%20network)).

Memory shortfalls can also occur if the basis set is large or if higher-order SAPT terms are included. SAPT2+(3) with charge transfer (as in `energy('sapt2+(3)-ct')`) is an order of magnitude more expensive than SAPT0. In one report, a user attempted SAPT2+(3) with a heavy atom (iodine) in the system. Psi4 printed an estimated memory usage of ~61843 MB and then crashed with a PSIO error ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=Estimated%20memory%20usage%3A%2061843)) ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=RuntimeError%3A%20Fatal%20Error%3A%20PSIO%20Error,recent%205%20function%20calls%20were)). The developer noted _“the memory estimate is quite far off”_ and concluded the job likely ran out of memory despite 80 GB being allocated ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=jmisiewicz%20%20August%201%2C%202019%2C,3%3A30pm%20%202)). High-order SAPT can generate very large arrays (for triple excitations, etc.) that sometimes exceed the initial estimate.

**Solutions:**

- **Use Density Fitting (DF) / J-K extrapolation:** Always ensure `SCF_TYPE DF` for the monomer SCFs ([sSAPT0 issues: out of disk - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/ssapt0-issues-out-of-disk/1603#:~:text=geometry%2C%20since%20your%20system%20is,integrals%20for%20the%20SCF%20calculation)), which Psi4 defaults to in recent versions when a suitable JK-fit basis is known. Density-fitting the SCF drastically reduces memory and disk I/O by avoiding storing full 4-index integrals. Likewise, the SAPT code itself will use density-fitted 2-electron integrals for many terms if you supply `df_basis_sapt` and `df_basis_elst` (which default to appropriate auxiliary bases for most common orbital bases ([SAPT: Symmetry-Adapted Perturbation Theory](https://psicode.org/psi4manual/master/sapt.html#:~:text=May%202022%20c,The%20reasoning%20and%20reward))). In short, **density fitting is nearly mandatory for large SAPT jobs** – without it, the integral storage will balloon. One forum answer states: _“include `set scf_type df` to use memory-efficient integrals for the SCF calculation”_ and emphasizes setting scratch properly ([sSAPT0 issues: out of disk - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/ssapt0-issues-out-of-disk/1603#:~:text=geometry%2C%20since%20your%20system%20is,integrals%20for%20the%20SCF%20calculation)).
    
- **Allocate more memory to Psi4:** The `memory` keyword in Psi4 input should be set to as much as you can afford for the job (keeping some headroom for OS). If you don’t specify enough, Psi4 might attempt out-of-core algorithms that strain disk. Note that Psi4 prints an **“Estimated memory usage”** at the start of SAPT; this is a rough guess. In one case, Psi4 estimated ~746 MB but still crashed on a 64-GB node ([SAPT Memory Problem - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-memory-problem/1013#:~:text=The%20troubling%20thing%20is%20that,900%20gigabytes)) – likely because the scratch directory was not set and /tmp filled up. Generally, if a job fails with memory error, try increasing `memory` in the input and ensure your scratch disk can handle large temporary files.
    
- **Set `PSI_SCRATCH` to a large local directory:** This is crucial on HPC clusters. By default, if `PSI_SCRATCH` isn’t set, Psi4 might use a small default directory. By pointing it to, say, a path in `/scratch/$USER/psi4_scratch`, you avoid writing to a potentially small or network-mounted partition. One expert noted: _“2 TB of disk space should be plenty for this size molecule (~200 atoms)... But the default behavior is to write to `/tmp`, which may not be very big.”_ ([sSAPT0 issues: out of disk - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/ssapt0-issues-out-of-disk/1603#:~:text=Another%20common%20problem%20is%20failing,these%20files%20over%20the%20network)) If you see PSIO errors, double-check this environment variable.
    
- **Reduce SAPT order or use natural orbital truncation:** If you requested a very high-level SAPT method, consider whether you need all those terms. SAPT0 or SAPT0+dispersion (DF-SAPT) is much cheaper than SAPT2+3. In the iodine SAPT2+(3)-ct example, the developers themselves asked _“Do you really need the component breakdown from SAPT2+(3)? SAPT0 generally gives good qualitative components, while for overall interaction energy, CCSD(T) will be more accurate.”_ ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=I%20was%20just%20testing%20this,3)) ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=you%20really%20need%20the%20components,3)). This hints that SAPT2+3, while available, is pushing the limits in terms of cost. Psi4 does have built-in **natural orbital truncation** for certain SAPT computations (enabled by default) that can cut down the virtual orbital space based on occupancy (with negligible impact on final energies) ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=Estimated%20memory%20usage%3A%2061843)). The default truncation threshold is 1e-6; if you encounter memory issues, you might even tighten this (e.g. 1e-5) to discard more tiny amplitude virtuals, saving memory.
    
- **Freeze core orbitals:** By setting `freeze_core true`, the SCF and subsequent SAPT will exclude core electrons from correlation calculations (e.g. in dispersion). This reduces the size of MP2/SAPT amplitude arrays and can save both memory and CPU. It’s generally recommended for SAPT unless you specifically need core-core interaction components (which are usually very small for intermolecular forces).
    
- **Parallel disk strategy:** If the issue is not total space but I/O speed, one can attempt to run SAPT on a machine with faster I/O or split across disks (though Psi4 does not natively stripe files across disks). In practice, ensuring local scratch (not a network filesystem) provides the best I/O performance.
    

**Quantitative trade-offs:** Using density fitting has a _huge_ payoff – it can reduce memory/disk by orders of magnitude with negligible error (on the order of microhartrees for energy). The trade-off is a tiny loss of precision, which is irrelevant for most SAPT analyses that report energies in the kcal/mol range. Freezing core has virtually no downside for intermolecular energies (it mainly leaves out core-core dispersion which is minute). Natural orbital truncation at 1e-6 is also designed to sacrifice at most ~0.01 kcal/mol in fringe cases ([SAPT: Symmetry-Adapted Perturbation Theory](https://psicode.org/psi4manual/master/sapt.html#:~:text=Caution)), in exchange for big speedups.

On the flip side, if you absolutely need a very high-accuracy SAPT2+3 result, be prepared for long runs and heavy resource usage. One might have to resort to segmented runs (e.g. compute dispersion separately from exchange) if memory doesn’t allow doing everything in one go. However, most users find SAPT0 or SAPT(DFT) with moderate basis sets (aug-cc-pVDZ/jun-cc-pVDZ) is tractable with <100 GB memory and a few hundred GB of disk at most ([sSAPT0 issues: out of disk - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/ssapt0-issues-out-of-disk/1603#:~:text=Another%20common%20problem%20is%20failing,these%20files%20over%20the%20network)). If you’re consistently hitting memory errors even with DF on, consider that as a sign to simplify the calculation.

## Basis Set and Compatibility Issues

Choosing a basis set for SAPT is a bit more involved than for a standard single-point energy, because you must consider not only the orbital basis for each monomer but also the fitting bases for various SAPT terms (electrostatics, exchange, induction, dispersion). Psi4 tries to choose reasonable defaults – for example, by default `DF_BASIS_SAPT` (for dispersion/induction) will use the RI-MP2 auxiliary basis of the orbital basis, and `DF_BASIS_ELST` (for Coulomb term) uses the JK-fit basis ([SAPT: Symmetry-Adapted Perturbation Theory](https://psicode.org/psi4manual/master/sapt.html#:~:text=May%202022%20c,The%20reasoning%20and%20reward)). Nevertheless, issues can arise:

- **Diffuse basis functions and linear dependence:** If you use an excessively diffuse basis (like aug-cc-pV5Z on a small molecule), the overlap matrix of atomic orbitals can have very small eigenvalues. This leads to numerical linear dependencies that can wreak havoc on SCF convergence and SAPT computations. Psi4 will by default remove linear dependent combinations using canonical orthogonalization with a cutoff (`S_TOLERANCE` default 1e-7) ([SCF](https://psicode.org/psi4manual/master/autodir_options_c/module__scf.html#:~:text=S_TOLERANCE%20%2059)) ([HF: Hartree–Fock Theory](https://psicode.org/psi4manual/1.5.0/scf#:~:text=Minimum%20eigenvalue%20in%20the%20overlap,of%20287%20possible%20MOs%20eliminated)). If the cutoff is too loose, nearly dependent functions remain and can cause SCF oscillations or poor convergence; if it’s too tight, you might remove functions unnecessarily. Tuning `S_TOLERANCE` can sometimes help: e.g. if SCF is unstable due to a near-dependence, set `s_tolerance 1e-6` to be more aggressive in culling diffuse functions. In extreme cases, you might omit the most problematic diffuse functions (for instance, use aug-cc-pVDZ on one monomer that needs it, but cc-pVDZ on a monomer that doesn’t, or manually remove a diffuse _s_ on a heavy atom, etc.).
    
- **Missing auxiliary bases:** Most standard orbital bases up to aug-cc-pVTZ have corresponding JK-fit (for SCF) and RI-fit (for MP2) bases in Psi4’s library. However, if you use a very new or uncommon basis set (or a custom one), Psi4 might not find a matching DF basis and will revert to exact algorithms. This can dramatically increase memory use (triggering the issues above). The solution is to manually specify a suitable auxiliary basis. For example:
    
    ```python
    set df_basis_scf cc-pvdz-jkfit      # use a J/K fitting basis for SCF
    set df_basis_sapt cc-pvdz-ri       # use RI basis for SAPT dispersion/induction
    set df_basis_elst cc-pvdz-jkfit    # use JK-fit for electrostatics
    ```
    
    (In many cases, simply setting the global `basis` will auto-select the others if named consistently, but specifying ensures no ambiguity.)
    
- **Effective Core Potentials (ECPs):** Using ECPs in SAPT has historically been tricky. Early Psi4 versions did not support ECPs in SAPT, but newer versions do allow it (there is even a sample input for SAPT with ECP on iodine ([psi4/samples/sapt-ecp/input.dat at master - GitHub](https://github.com/psi4/psi4/blob/master/samples/sapt-ecp/input.dat#:~:text=psi4%2Fsamples%2Fsapt,ecp%2Finput.dat%20at%20master%20%C2%B7%20psi4%2Fpsi4)) ([psi4/samples/sapt-ecp/input.dat at master - GitHub](https://github.com/psi4/psi4/blob/master/samples/sapt-ecp/input.dat#:~:text=psi4%2Fsamples%2Fsapt,ecp%2Finput.dat%20at%20master%20%C2%B7%20psi4%2Fpsi4))). The primary issue with ECPs is ensuring that the underlying SCF can handle them. If the ECP basis lacks a proper JK fit basis, SCF_TYPE DF may not be possible. In a forum query about SAPT with an iodine ECP, the user provided `def2-TZVP` with ECP and corresponding `def2-tzvp-jkfit` and `def2-tzvp-ri` for DF ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=set%20globals%20%7B%20basis%20def2,ct%E2%80%99)), which is correct. The job still failed with a memory error (due to overall size) ([SAPT with ECP for Iodine atom - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-with-ecp-for-iodine-atom/1482#:~:text=RuntimeError%3A%20Fatal%20Error%3A%20PSIO%20Error,recent%205%20function%20calls%20were)), but not due to incompatibility. The takeaway is: **if using ECPs, always include the appropriate ECP-capable auxiliary bases** (e.g. the def2 family has them). If none exists, you may have to switch off DF (not recommended) or use an all-electron basis as a workaround. Keep an eye on the output for any messages about basis sets being dropped or not found.
    
- **SAPT(DFT) specific settings:** In SAPT(DFT) (where monomer references are DFT, often with an exchange-correlation potential for dispersion), there is an extra parameter: the **GRAC shift**. This is a correction added to the DFT monomer Hamiltonian to mimic the ionization potential (IP) difference, and it must be set by the user for each monomer. If you neglect to set `sapt_dft_grac_shift_a` and `_b`, Psi4 will likely proceed with a default (zero) shift, which can lead to unphysical results or convergence issues. One user reported a SAPT(DFT) on He–Ar giving nonphysical positive energies for the He monomer SCF ([SAPT (DFT) issues - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-dft-issues/1444#:~:text=which%20He%20atom%20and%20Ar,I%20got%20in%20Iter%208)). They had provided GRAC shifts (0.32033 and 0.19999 for He and Ar) yet the He’s SCF still plateaued incorrectly ([SAPT (DFT) issues - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-dft-issues/1444#:~:text=RKS%20part%20for%20the%20He,I%20got%20in%20Iter%208)) ([SAPT (DFT) issues - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/sapt-dft-issues/1444#:~:text=set%20%7B%20basis%20aug,19999)). This suggests the SAPT(DFT) code was (at that time) still finicky. By 2021, documentation clarified how to compute GRAC shifts (difference between true IP and negative HOMO energy) ([GRAC shift calculation clarification for SAPT-DFT - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/grac-shift-calculation-clarification-for-sapt-dft/2291#:~:text=,%E2%80%9D)) ([GRAC shift calculation clarification for SAPT-DFT - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/grac-shift-calculation-clarification-for-sapt-dft/2291#:~:text=The%20KS%20HOMO%20is%20simply,neutral%E2%80%A6which%20will%20generally%20be%20negative)), and getting these right is crucial for SAPT(DFT) reliability. So, ensure you consult the latest Psi4 manual for SAPT(DFT) and set those shifts properly – otherwise SCF might struggle since the DFT monomer potential is effectively missing a term.
    

**Recommended practices:** For most closed-shell SAPT0 cases, a good choice is the jun-cc-pVDZ or jun-cc-pVTZ basis (these are “jun” = truncated augments optimized for SAPT). They are designed to balance accuracy and cost, and Psi4 has all needed auxiliary fits for them. Users have had many successes with jun-cc-pVDZ in Psi4 SAPT0 (it’s kind of a “default” in examples). If jun-cc-pVDZ SCF has trouble converging due to diffuse functions (which is rare), you can drop to cc-pVDZ for the SCF, then perhaps add diffuse functions perturbatively. But an easier fix is using the `BASIS_GUESS` feature: as shown above, it will do a preliminary SCF with a smaller basis (like 3-21G) and project the orbitals to jun-cc-pVDZ ([SCF](https://psicode.org/psi4manual/master/autodir_options_c/module__scf.html#:~:text=BASIS_GUESS%20%2062)). One user essentially tried to do this manually by first converging a smaller basis and then reading the guess for the larger basis ([SCF guess read ---fresh man - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-guess-read-fresh-man/1479#:~:text=I%20have%20tried%20other%20method,pvdz)) – with `basis_guess` this is automated.

Finally, be cautious mixing very different basis sets on the two monomers. Psi4’s SAPT expects one common dimer basis encompassing both monomers (it uses the dimer centered AO basis for monomer calculations to avoid basis set superposition error). So, you typically specify one basis for the whole dimer. If you have a reason to use different basis sets for each fragment, you’d need to use the more advanced FISAPT module or do monomers separately – but that’s beyond normal SAPT0 usage. In short, pick a single well-behaved basis and ensure all needed fitting sets are available.

## Geometry-Induced Numerical Instability

Even if your system is formally a closed-shell dimer, the _actual geometry and structure_ can lead to SCF or SAPT difficulties:

- **Fragment with dangling bonds or unrealistic structure:** If you cut a piece out of a molecule and treat it as a fragment without saturating bonds, you might think it’s closed-shell by electron count, but it could in fact harbor a high-energy electronic structure (basically an open-shell character or at least a very high-lying HOMO). An example from the Psi4 forum showed a user trying SAPT on a graphene fragment that had many edge carbon atoms with unsatisfied valences. The SCF would not converge. The advice was blunt: _“Fix your structure! You don’t have a closed shell molecule with all those cut bonds. It’s a highly reactive fantasy molecule. Saturate the dangling bonds...”_ ([SCF doesn't convergence - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-doesnt-convergence/1821#:~:text=As%20I%20said%20in%20the,sheet%20to%20reduce%20edge%20effects)). The user followed this advice (adding hydrogens to the fragment edges) and reported _“It really does work.”_ – the SCF converged and SAPT ran ([SCF doesn't convergence - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-doesnt-convergence/1821#:~:text=You%20don%E2%80%99t%20have%20a%20closed,sheet%20to%20reduce%20edge%20effects)).
    
    The moral is: **make sure each monomer is a realistic closed-shell species.** If they are fragments of a larger molecule, add hydrogens or modify them so that they are stable on their own. Not only will SCF converge more easily, but the SAPT interpretation (electrostatics, etc.) will be more meaningful.
    
- **Unoptimized or strained geometries:** A geometry far from equilibrium can cause SCF problems. For instance, an X-ray structure with some bad contact or an arbitrary placement of two molecules might lead to very large repulsive interactions. SCF is a nonlinear procedure that assumes a reasonable starting point. Extremely close intermolecular distances can cause the initial guess (like SAD) to be way off (since electron density clouds overlap strangely). If you suspect this, try increasing the distance a bit to see if SCF converges. If it does, you know the original geometry might be too extreme. Alternatively, do a rough optimization (even at a low level like HF/sto-3g or using molecular mechanics) to relax any severe clashes before running SAPT.
    
- **Coordinate unit mix-ups:** Always double-check that the `units` (Angstrom or Bohr) are correctly specified in the Psi4 input for the molecule. If one provides atomic coordinates assuming Angstroms but Psi4 treats them as Bohr (default is Angstrom unless specified), the geometry will be off by a factor of ~0.529. Too large distances (if you accidentally gave Bohr values in Angstrom mode) might make monomers non-interacting – SCF will still converge (likely easily, since each monomer is basically isolated), but SAPT results will be trivial. Too small distances (Angstrom given but interpreted as Bohr, meaning ~half the intended distance) can make SCF struggle or even converge to a weird charge-separated state. So this is a silent gotcha to avoid.
    
- **High symmetry and degeneracies:** In rare cases, if a monomer has a high symmetry, the SCF might have degenerate orbitals that mix and cause convergence swings. Psi4’s SCF is usually robust with symmetry, but if you suspect this, you can tell Psi4 to use `symmetry c1` (no symmetry) for the monomer calculations to remove degenerate subspaces. This can help if, say, an alternant conjugated system has two equal HOMOs and the SCF oscillates between different broken-symmetry combinations. By lowering symmetry and perhaps using MOM to stick to one configuration, you can reach convergence.
    

**Example & resolution:** The earlier example of the graphene fragment is a clear case where geometry was the root cause of SCF failure ([SCF doesn't convergence - SAPT - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-doesnt-convergence/1821#:~:text=As%20I%20said%20in%20the,sheet%20to%20reduce%20edge%20effects)). Another user had an SCF that “doesn’t converge” even after many iterations, on what they thought was a proper system. On examination, it turned out to be an **unoptimized cluster geometry** they imported. The large SCF oscillations tipped off the Psi4 team that _“something is quite wrong… Is this an unoptimized crystal structure? … Or a difficult electronic state?”_ ([SCF guess read ---fresh man - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-guess-read-fresh-man/1479#:~:text=hokru%20%20July%2024%2C%202019%2C,2%3A57pm%20%204)). After the user optimized the structure (and confirmed the spin state was correct), the SCF converged ([SCF guess read ---fresh man - Psi4 – Open-Source Quantum Chemistry](https://forum.psicode.org/t/scf-guess-read-fresh-man/1479#:~:text=I%20have%20optimazed%20in%20Gaussian,very%20thankful%20to%20your%20help)).

In summary, for geometry-induced issues the recovery is usually outside the quantum software: fix the molecular structure itself. Ensure each monomer is stable and well-behaved in isolation. If you can run a simple HF/DFT energy on each monomer without SAPT and those converge, then any further issues lie elsewhere. It’s a good practice to run `energy('hf')` or `energy('DFT')` on each fragment as a sanity check before doing SAPT – this isolates pure SCF convergence of your geometry. If those single-molecule calculations have trouble, resolve that (either by geometry changes or SCF tricks above) first, then proceed to SAPT.

## Recovery Strategy Trade-offs and Cross-Software Insights

Throughout the above discussions, we noted some trade-offs (e.g. damping vs. level shift, SOSCF vs. DIIS). Here we collect a few key points and also mention analogous strategies in other quantum chemistry packages:

- **Damping vs. Level Shift:** Both are techniques to stabilize SCF. Damping (in Psi4, turned off by default but easily enabled) directly reduces oscillations and is recommended to use liberally ([SCF](https://psicode.org/psi4manual/master/autodir_options_c/module__scf.html#:~:text=,18)). It doesn’t bias the solution except slowing down updates slightly. Level shifting biases the solution by pushing virtual orbitals up in energy; it _guarantees_ convergence in theory ([HF: Hartree–Fock Theory](https://psicode.org/psi4manual/1.5.0/scf#:~:text=A%20commonly%20used%20alternative%20to,DIIS%20error%20is%20smaller%20than)), but one must remove the shift to get the true energy. A common tactic (used in Molpro, QChem, etc.) is to apply a level shift for the first N iterations, then turn it off. Psi4’s `LEVEL_SHIFT_CUTOFF` automates this by turning off the shift when the SCF error gets below a threshold ([HF: Hartree–Fock Theory](https://psicode.org/psi4manual/1.5.0/scf#:~:text=most%20useful%20in%20the%20initial,2%2C%20respectively)). If you use a large shift, be sure that threshold is not too high, or you might inadvertently converge to a slightly excited state (because a huge shift can prevent the HOMO/LUMO from mixing even when they need to). In practice, a 5.0 Hartree shift with a cutoff of 1e-2 or 1e-3 is a good starting point ([HF: Hartree–Fock Theory](https://psicode.org/psi4manual/1.5.0/scf#:~:text=most%20useful%20in%20the%20initial,2%2C%20respectively)).
    
- **SOSCF (Newton) vs. DIIS (Pulay):** DIIS is very fast per iteration and usually reliable, but can fail for very pathological cases (getting stuck in a cycle). SOSCF is more expensive but has a larger radius of convergence. Some programs (Q-Chem, ORCA) offer augmented schemes that blend quasi-Newton steps with DIIS – in Psi4, you might emulate this by running a bit of SOSCF, then switching to DIIS. For example, if DIIS stagnates, you could do:
    
    ```python
    set soscf true
    set maxiter 5
    energy('hf')  # a few SOSCF iterations
    set soscf false
    set guess read
    set maxiter 50
    energy('hf')  # resume with DIIS from SOSCF solution
    ```
    
    This is analogous to Q-Chem’s ABINITio+DIIS or ORCA’s SOSCF start. It’s manual in Psi4, but effective if needed.
    
- **Basis set truncation vs. augmentation:** Sometimes less is more – a smaller basis (without diffuse functions) might converge SCF easily, whereas an augmented basis does not. One strategy is to converge in a smaller basis then use those orbitals as a guess for the larger basis. Psi4’s `BASIS_GUESS` (which defaults to 3-21G or def2-SV(P) as a small basis) automates one round of this ([SCF](https://psicode.org/psi4manual/master/autodir_options_c/module__scf.html#:~:text=BASIS_GUESS%20%2062)). If that fails, you might try an even more customized two-step: e.g. run an SCF in cc-pVDZ (no diffuse) to convergence, then use those orbitals as the starting point for aug-cc-pVDZ. This often succeeds because the initial density is already close to correct, and the diffuse functions just fine-tune it. The trade-off is the extra computation for the small-basis SCF, but that is usually negligible compared to a stuck big-basis SCF that never converges.
    
- **Cross-software SCF:** Molpro is known for very robust SCF convergence algorithms (it has tightening of DIIS, damping, etc., often converging cases other programs can’t). Q-Chem also has advanced SCF routines including MOM for excited states and stability analysis. If you have access to those, you can use them to get monomer orbitals and import into Psi4 as discussed. Standalone SAPT codes (SAPT2016/SAPT2020 from the Sapthorn/UCF group or the Warsaw group) require you to input monomer densities or wavefunctions, which forces the user to solve SCF separately. That workflow can be leveraged: you could use, say, Q-Chem to get a PBE0 density for each monomer (because Q-Chem might handle a tricky open-shell or diffuse case better), then use that density in Psi4 SAPT(DFT). While Psi4 does not directly read external densities, one could do a near-zero-step SCF by feeding an extremely close guess. One idea is to convert the external orbitals to a Molden file and use Psi4’s `integral_projection` (if available) or guess read to construct the Psi4 wavefunction.
    
    In essence, **the techniques to fix SCF convergence in Psi4 are very similar to those in other codes**, and what you learn in one context transfers to another. If Psi4 lacks an automated feature that another program has, you can often reproduce it with a bit of Python scripting around the Psi4 call (as shown in examples).
    
- **SAPT-specific basis considerations:** In Molpro’s SAPT module, one also must pick fitting functions for dispersion (Molpro uses density fitting by default for SAPT0). The philosophy is the same: use the recommended auxiliary basis sets (usually given in the manual) to avoid huge memory use. The Psi4 manual’s caution from August 2021 highlights that using the proper JKFIT for electrostatics made SAPT0 results more physical ([SAPT: Symmetry-Adapted Perturbation Theory](https://psicode.org/psi4manual/master/sapt.html#:~:text=May%202022%20c,The%20reasoning%20and%20reward)). That was an insight carried over from the SAPT(FISAPT) code: a better description of the exchange-hole for electrostatics required a different fit basis. Psi4 now does that automatically, but if you’re using an older Psi4, keep an eye on those options – you might manually set `df_basis_elst` to the JKFIT of your orbital basis to improve stability ([SAPT: Symmetry-Adapted Perturbation Theory](https://psicode.org/psi4manual/master/sapt.html#:~:text=May%202022%20c,The%20reasoning%20and%20reward)).
    

## Open-Shell SAPT Failures and Future Outlook

While our focus is on closed-shell systems, it’s worth noting that open-shell SAPT (where one or both monomers have unpaired electrons) introduces additional challenges. Open-shell SCF (UHF or ROHF) is inherently more prone to convergence issues and instabilities (e.g., spin contamination, multiple nearly degenerate solutions). Psi4’s SAPT0 can handle open-shell (e.g. a doublet-quartet interaction), but users have reported errors like the aforementioned “Matrix is not SPD” which was traced to an UHF instability ([SAPT: Matrix is not SPD · Issue #1682 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1682#:~:text=Hello%20everyone%2C%20So%20this%20is,the%20correct%20solution%20to%20SAPT)). The solution was to perform a UHF stability analysis and follow the lower solution ([SAPT: Matrix is not SPD · Issue #1682 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1682#:~:text=We%20now%20have%20a%20reproducible,SAPT%20completes%20with%20no%20problems)). At one point, there was even a bug in Psi4’s stability follow for UHF that required manually intervening ([UHF-SAPT0 instability · Issue #1747 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1747#:~:text=It%20is%20just%20a%20coincidence,in%20the%20OP%20example%20well)). The guidance from developers was: _“As long as the (suspected) bug in the stability following is not solved, UHF calculations might need manual massaging… Try different guesses, add damping, use SOSCF, etc.”_ ([UHF-SAPT0 instability · Issue #1747 · psi4/psi4 · GitHub](https://github.com/psi4/psi4/issues/1747#:~:text=As%20long%20as%20the%20,calculations%20might%20need%20manual%20massaging)). In practice, one might need to converge each monomer’s UHF with care, possibly freeze core and use symmetry-breaking if needed, then feed into SAPT. SAPT(DFT) for open-shell (e.g. radical interactions) is even newer and may not be fully black-box yet.

Looking ahead, improvements continue to be made. By Psi4 1.8+, many of the earlier bugs have been addressed. However, open-shell SAPT often requires using high-spin ROHF references or even state-specific methods if the radicals form a complex. This remains an area of active development and users attempting it should be prepared to apply all the tricks in the book (and consult updated Psi4 forums for the latest patches or advice specific to open-shell cases).
