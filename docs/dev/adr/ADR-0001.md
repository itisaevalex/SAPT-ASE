# ADR-0001: Core Data Models and Workflow Architecture for SAPTASE MVP

## Status

Accepted

## Context

The SAPTASE project aims to provide a robust framework for automating Symmetry-Adapted Perturbation Theory (SAPT) calculations with adaptive basis sets, error recovery, and multi-fidelity approaches. As outlined in the Development Workflow Guide, the first milestone is to deliver a Minimum Viable Prototype (MVP) that demonstrates end-to-end data flow from task definition to result generation using Psi4 as the computational backend.

The core architectural decisions for this MVP revolve around:
1. How to represent molecules, tasks, and results
2. How to define backend interfaces for different SAPT implementation packages
3. How to structure the workflow for executing SAPT calculations

## Decision

We have decided to implement the MVP with the following core architecture:

### 1. Data Models

- **Molecule**: A dataclass representing a molecular structure with:
  - Atom symbols and 3D coordinates
  - Charge and multiplicity
  - Methods for conversion to/from XYZ format

- **SaptTask**: A dataclass representing a SAPT calculation task with:
  - References to two monomer molecules
  - Basis set and method specifications
  - Task status tracking
  - Additional backend-specific keywords

- **SaptResult**: A dataclass for storing calculation results with:
  - Energy components dictionary (electrostatics, exchange, induction, dispersion, total)
  - Success/failure status and error messages
  - Methods for accessing energies in different units

### 2. Backend Interface

- **SaptBackend** (Abstract Base Class): Defines the interface for all SAPT calculation backends
  - `calculate(task: SaptTask) -> SaptResult`: Main method to be implemented by concrete backends

- **Psi4Backend**: Implementation of SaptBackend using Psi4
  - Sets up Psi4 with the appropriate molecule fragments, basis, and options
  - Runs SAPT0 calculation and extracts energy components

- **Placeholder backends** for CamCASP and SAPT2020 (to be implemented later)

### 3. Workflow Structure

- **SaptWorkflow**: Class for managing multiple SAPT tasks
  - `add_task(task)`: Add a SAPT calculation task
  - `add_dimer(monomer_a, monomer_b, ...)`: Convenience method to create and add a task
  - `run_local_serial()`: Execute all tasks sequentially on the local machine
  - `get_result(task_id)`: Retrieve results for a specific task

- **run_sapt()**: Convenience function for single calculations

### 4. Implementation Decisions

- Use dataclasses for clean, type-hinted data structures
- Implement proper error handling and status tracking
- Provide flexible interfaces for future extensions
- Keep a clear separation between data models, calculation backends, and workflow logic
- Make the Psi4 backend work with a fixed basis set (jun-cc-pVDZ) for MVP

## Consequences

### Positive

- Clean separation of concerns makes the codebase maintainable and testable
- Abstract backend interface allows for future support of different SAPT implementations
- Type hints improve code quality and IDE support
- The design supports both workflow and single-calculation usage patterns
- The architecture is extensible for future features like adaptive basis selection, error recovery, etc.

### Negative

- Additional complexity compared to a simple script-based approach
- The MVP does not yet implement advanced features like adaptive basis selection or error recovery
- Backend abstractions introduce some overhead

### Neutral

- The decision to use dataclasses over other approaches (like Pydantic) is pragmatic for MVP but may be revisited
- The fixed basis set (jun-cc-pVDZ) is appropriate for MVP but will be made adaptive in future versions

## Further Work

After the MVP is implemented and validated, subsequent phases will add:
1. Adaptive basis selection logic
2. Error recovery ladder for SCF convergence issues
3. Parallel execution capabilities
4. Multipole analysis and ML surrogate integration
5. Enhanced documentation and examples
