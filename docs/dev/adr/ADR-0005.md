# ADR-0005: Choice of Distributed Execution Framework

*   **Status**: Proposed
*   **Date**: 2025-04-23
*   **Deciders**: Alex Isaev, Cascade
*   **Context**: The `saptase` project requires a mechanism to scale computations beyond a single machine to handle high-throughput workflows involving potentially thousands of independent SAPT calculations. The existing local parallel execution (`ProcessPoolExecutor`) is insufficient for cluster environments.
*   **Decision**: We will standardize on `dask.distributed` as the primary framework for distributed execution in `saptase`.
*   **Consequences**:
    *   Introduces Dask as a core dependency (`dask[distributed]`).
    *   Requires implementation of a `DaskExecutor` conforming to the existing executor interface.
    *   Allows leveraging Dask's flexibility for various cluster types (local, SLURM, etc.) through libraries like `dask-jobqueue`.
    *   Development and testing can utilize `dask.distributed.LocalCluster` for simplicity.
    *   Production deployments can target existing Dask schedulers or dynamically launch workers via `dask-jobqueue` (e.g., `SLURMCluster`).
    *   The existing `ProcessPoolExecutor` path will be retained for simple local parallelism and as a fallback.
*   **Alternatives Considered**:
    *   **AiiDA**: Powerful workflow engine for computational science, but introduces significant complexity and overhead compared to Dask for our specific need of parallel task submission.
    *   **Parsl**: Python parallel scripting library, similar goals to Dask but potentially less mature ecosystem and community support.
    *   **Ray**: Distributed execution framework with a focus on AI/ML workloads. While capable, Dask feels more aligned with general-purpose scientific Python task scheduling.
    *   **Plain SLURM array jobs**: Simple for embarrassingly parallel tasks but lacks dynamic scheduling, fault tolerance, and the richer diagnostic tools provided by Dask.
*   **Rationale**: `dask.distributed` offers a good balance of power, flexibility, and ease of integration with the existing Python ecosystem. It provides:
    *   Dynamic task scheduling.
    *   Resilience to worker failures.
    *   A comprehensive dashboard for monitoring.
    *   Support for various cluster managers via `dask-jobqueue`.
    *   A relatively straightforward API for submitting functions (`client.submit`).
    *   Seamless transition from local development (`LocalCluster`) to production clusters.
