# ADR-0005  Distributed Execution Framework

**Date:** 2025-04-23  
**Status:** Accepted (implemented in Phase 5b)

---

## 1  Context ☁️

Local `ProcessPoolExecutor` works for ≤ 8 cores, but we now need to drive **hundreds–thousands** of SAPT jobs across HPC nodes.

Requirements:

* *Pure‑Python* runtime – no custom MPI/C++
* *Dynamic DAG* – tasks appear as adaptive ladder & retries fire
* *Easy switch* between laptop (LocalCluster) and SLURM clusters
* Keep per‑task provenance (LogDb writes from workers)

---

## 2  Decision ✅

Adopt **`dask.distributed`** as the distributed execution layer.

* Dev / CI → `LocalCluster`
* HPC → `dask_jobqueue.SLURMCluster`
* Provide thin adapter `DaskExecutor` so orchestrator can call `submit_task()` like it does for the local path.

---

## 3  Rationale 🤔

| Option | + | – | Verdict |
| --- | --- | --- | --- |
| **Dask** | Python‑native, dynamic graph, SLURM plugin, dashboard | Need to watch worker memory; serialisation pitfalls | **Chosen** |
| Ray | Similar scaling, nice API | Heavier runtime, weaker SLURM story | No |
| Parsl | Abstraction nice | Thin community, limited UI | No |
| AiiDA / FireWorks | Proven lineage DB | Overkill – duplicates LogDb | No |
| Plain SLURM array | Simple | No dynamic retries, no Python callback path | No |

Interaction with current executor path:

```
auto
 ├─ if scheduler addr found → run_dask()
 └─ else                   → run_local_parallel()
```

---

## 4  Consequences 🔄

* **Pros** – Seamless dev‑to‑cluster, one dep (`dask[distributed]` + `dask_jobqueue`), reuse picklable models.
* **Cons/Risks** – Psi4 not fork‑safe ⇒ call `psi4.core.clean()`; SQLite on network FS ⇒ use `check_same_thread=False`.

---

## 5  Implementation 🛠️

1. `saptase/execution/dask.py` – owns a Client/Cluster, exposes `submit_task` & `close`.
2. `SaptWorkflow.run_dask()` mirrors `run_local_parallel` but via `DaskExecutor`.
3. Config knobs (`execution.mode`, `execution.dask.scheduler`, `execution.dask.n_workers`).
4. Unit tests marked `@pytest.mark.dask`; CI job installs Dask and runs them.

---

## 6  Decision Acceptance Criteria 🎯

* All new tests pass locally and in CI.
* `examples/dask_cluster.yml` runs 4 mock jobs on laptop.
* `saptase run job.yml --mode dask` works by auto‑detecting scheduler address.

## 8  Implementation Status 🚀

Phase 5b (April 24 2025) delivered the first production implementation:

* `DaskExecutor` wrapper and `SaptWorkflow.run_dask()` merged.
* Scratch-directory isolation via nested-safe `TaskScratch` now active on every worker.
* LogDb switched to SQLite **WAL** mode with 10 s busy-timeout for multi-process safety.
* Configuration surface exposed under `scratch:` in `saptase/config.py` and YAML job files.
* Full test-suite (incl. Dask unit tests) green on Linux & Windows CI.

**Post-Phase 5b Hardening (April 26 - May 1 2025):**
- Addressed intermittent `LocalCluster` leaks by refining `DaskExecutor.close` / `__exit__` logic, including explicit `gc.collect()` calls and using `dask.distributed.utils.sync` for robust shutdown.
- Fixed stress tests (`tests/test_dask_stress.py`) to correctly use the `DaskExecutor` context manager and pass the scheduler address, eliminating the final persistent leak.
- Added comprehensive leak detection fixtures (`assert_no_leaked_dask_cluster`) to CI.

The ADR is therefore marked **Accepted**.
