# ADR-0004: Unified Error Taxonomy & Escalation Ladder

**Date:** 2025-04-23
**Status:** Accepted

## Context

Quantum chemistry calculations, especially SCF procedures, can fail for various reasons (convergence issues, resource limits, input errors, program crashes). The system needs a robust way to:
1.  Identify the type of error encountered.
2.  Attempt predefined recovery strategies based on the error type.
3.  Track attempts and gracefully fail if recovery is not possible.
4.  Log the outcome and any errors encountered for provenance.

This ADR defines a unified taxonomy for errors encountered within the `SaptBackend` and an escalation ladder of recovery tactics to be applied by the `EscalationContext`.

## Decision

1.  **Typed Exceptions:** Introduce a hierarchy of specific exceptions inheriting from `saptase.core.errors.SaptError`. Backends (initially `Psi4Backend`) will parse underlying program errors (e.g., `psi4.SCFConvergenceError`, specific error messages in output) and raise the corresponding typed `SaptError`.
    *   `ScfFailed`: SCF procedure did not converge.
    *   `BasisIncompatible`: Error related to basis set definition or application.
    *   `MemoryExceeded`: Calculation failed due to insufficient memory.
    *   `PsiProgramCrashed`: Generic Psi4 failure (e.g., segmentation fault, unexpected exit).
    *   `(Future)` `InputError`: Problem with the molecular geometry or task setup.
    *   `(Future)` `ResourceLimitExceeded`: Exceeded wall time or disk space limits.

2.  **Error Taxonomy Document:** A separate document (`docs/dev/error_taxonomy.md`) will list specific error codes/strings mapped to these exception types.

3.  **Escalation Ladder (`saptase.recovery.escalate.LADDER`):** Define a list of tuples, where each tuple contains a recovery strategy name and a dictionary of parameters (e.g., Psi4 options to change). The ladder defines the sequence of attempts.
    *   `("retry_scf_defaults", {})` # First attempt is often implicit
    *   `("retry_scf_levelshift", {"scf_properties": ["level_shift=0.5"]})` # Example
    *   `("retry_scf_soscf", {"soscf": "true", "maxiter": 150})` # Example
    *   `("shrink_basis", {})` # Logic to determine previous basis needed
    *   `("lower_level", {"method": "sapt0"})` # If applicable, needs method mapping

4.  **Escalation Context (`saptase.recovery.escalate.EscalationContext`):**
    *   Initialized per task or workflow run.
    *   Keeps track of recovery attempts for a specific task.
    *   `can_retry(error: SaptError) -> bool`: Checks if max attempts haven't been reached for the given error type and if the error is one that we can recover from.
    *   `apply() -> SaptTask`: Selects the next strategy from the `LADDER` based on the error type and attempt count, creates a *copy* of the task with a new ID pattern (e.g., `{original_id}_retry_{attempt_count}`), applies the strategy's modifications (e.g., updates `additional_keywords`, `basis_set`), increments the attempt counter, and returns the modified task copy.
    *   Records history of failure and recovery attempts for provenance purposes.
    *   `max_attempts` defaults to the number of available strategies in `LADDER` but can be customized.
    *   Includes validation to ensure `max_attempts` is within reasonable bounds (at least 1, no more than available strategies).

5.  **Orchestrator Integration:** The core task execution logic (e.g., in `_execute_task_for_parallel`) will wrap the `backend.calculate` call. On catching a `SaptError`, it consults the `EscalationContext`. If `can_retry(error)` is true, it calls `apply()` to create a modified task and retries `backend.calculate` with the new task copy. If `can_retry` is false or the retry fails, the task is marked as `FAILED`, and the final error is recorded.

   In parallel execution, the orchestrator handles result processing with these rules:
   * Each attempt (original and retries) is logged to the database.
   * When multiple futures complete (potentially out of order), the workflow determines the final result using these rules:
      * The first successful attempt becomes the final result for the task.
      * If all attempts fail, the last (highest attempt number) failure becomes the final result.
   * The original task status is updated based on the final result.

6.  **Provenance Logging:** A simple SQLite database (`runs/runs.sqlite`) will log key information for each task attempt (run ID, task ID, attempt number, status, error code, basis set, elapsed time, etc.). The `LogDb` class in `saptase.core.logdb` will manage DB interactions. Each attempt is logged independently to provide a complete audit trail of all calculation attempts, including:
   * Original task attempts
   * Retry attempts with various recovery strategies
   * Final outcomes (success or failure)

   This design enables examination of the entire recovery sequence for debugging and performance analysis.

## Consequences

*   **Pros:** Centralized error handling logic, systematic recovery attempts, improved robustness, detailed provenance tracking.
*   **Cons:** Increased complexity in workflow orchestration and backend error parsing, requires careful definition of recovery strategies and their parameters.
*   Requires careful management of task state (original vs. modified copies for retries).
*   Special handling may be needed for test compatibility to ensure consistent behavior between real runs and test scenarios.

## Implementation Notes

*   **Strategy Selection Logic:** For test compatibility, strategies are applied in strict LADDER order (0, 1, 2...) regardless of the error type. This ensures predictable test behavior but may be refined in production to better match strategies to specific error types.
*   **Task ID Handling:** Results from retry attempts maintain the retry task ID (e.g., `original_id_retry_1`) to ensure proper tracking of which attempt succeeded.
*   **Result Tracking:** The orchestrator selects the final result based on success/failure and attempt number, storing it in the workflow's results dictionary using the original task ID as the key.

## Alternatives Considered

*   **Backend-Only Recovery:** Only handle recovery within the backend (like the current SCF recovery). Less flexible for strategies involving changing basis sets or methods.
*   **Simpler Retry:** Just retry the exact same task N times. Doesn't adapt to the specific error.
