# ADR-0002: Choice of Parallelism Framework for Local Execution

**Date:** 2025-04-22

**Status:** Accepted

## Context

SAPTASE needs to execute multiple independent SAPT calculations efficiently on a single multi-core machine. The primary target backend, Psi4, is CPU-bound and can utilize multiple threads internally via OpenMP (`OMP_NUM_THREADS`). However, running multiple Psi4 instances concurrently requires process-level parallelism to avoid GIL contention (in CPython) and potential conflicts if Psi4's internal state is not fully thread-safe across separate calls within the same process.

We need a standard Python library solution for managing a pool of worker processes to run these independent tasks.

## Decision

We will use Python's built-in `concurrent.futures.ProcessPoolExecutor` for implementing the `SaptWorkflow.run_local_parallel()` method.

## Rationale

- **Standard Library:** `concurrent.futures` is part of the Python standard library, requiring no additional external dependencies for basic parallel execution.
- **Process-Based:** It uses `multiprocessing` under the hood, providing true process-level isolation suitable for running external CPU-bound programs like Psi4.
- **Simplicity:** The `Executor.map` interface provides a straightforward way to apply a function (our SAPT task runner) to an iterable of inputs (the list of `SaptTask` objects).
- **Resource Control:** We can control the maximum number of worker processes (`max_workers`).
- **GIL Avoidance:** By using separate processes, we bypass the Global Interpreter Lock (GIL) limitations inherent in CPython's `threading` module, which would hinder performance for CPU-bound tasks.
- **Compatibility:** `multiprocessing` generally works well on major platforms (Linux, macOS, Windows), although Windows has specific considerations (e.g., object pickling, `if __name__ == '__main__':` guard).

## Alternatives Considered

- **`threading`:** Rejected due to the GIL, making it unsuitable for CPU-bound tasks like Psi4 calculations.
- **`Dask.distributed`:** More powerful and suitable for distributed execution across multiple machines, but adds a heavier dependency and complexity for the initial local parallel implementation. It remains an option for future scalability enhancements.
- **Custom `multiprocessing`:** Using the lower-level `multiprocessing.Pool` directly offers more control but `concurrent.futures` provides a simpler, higher-level API sufficient for our needs.

## Consequences

- **Pickling:** Objects passed between the main process and worker processes (like `SaptTask` and `SaptResult`) must be pickleable. This requires careful design of our data classes.
- **Worker Setup:** Each worker process will need to initialize its environment appropriately, including setting `OMP_NUM_THREADS=1` to prevent Psi4 instances from competing for cores within a single worker.
- **Windows:** Requires the standard `if __name__ == '__main__':` guard in the main script invoking the parallel execution.
- **Error Handling:** Errors raised in worker processes are propagated back to the main process via futures, requiring careful exception handling.
- **Overhead:** Process creation has more overhead than thread creation, but this is negligible compared to the runtime of typical SAPT calculations.
